## English summary

A reproducible, open-source **SDN intrusion/anomaly detection** project (Apache-2.0).

- **Self-contained data generator** — synthesises 8 classes of SDN flow traffic with
  inSDN / CICFlowMeter-compatible columns (84-col and 22-col schemas), physical-quantity
  consistency and difficulty knobs (class overlap, stealthy attacks, label noise).
- **CNN + BiLSTM dual-branch model** (sliding window `(T, F)`, multi-task heads for
  multi-class + binary, temporal attention), with ablations, multi-seed statistics,
  drift robustness and error analysis.
- **Deployment-oriented**: online alarm-level metrics (detection delay, false alarms per hour,
  attack-segment recall) and an **operating-point selector** that trades false alarms against
  latency — false alarms can be cut from 8.56 to **0.66 per hour** while keeping **100%**
  segment recall. In operations terms: **~36 alerts/day, ~3.6 analyst-hours/day**, mean
  detection delay **18 ms**.
- **Actually a system, not a notebook**: an online detection service (`POST /api/detect` with
  sliding buffer, threshold + N-of-M confirmation, throttling/blocking policy, whitelist,
  dry-run, JSONL audit trail, Prometheus `/metrics`), a **Ryu controller adapter**, and a
  no-Ryu controller simulator that measured **1,364–1,918 flows/s** end-to-end.
- **Reproducible**: one command (`python run_all.py`), **50-item acceptance self-check**,
  10 unit tests, offline demo dashboard, no GPU required (~0.02 ms per window batched).

Quick start: `pip install -r requirements.txt && python run_all.py --smoke` (≈25 s),
then `python app/app.py` for the live dashboard. See sections below for details.

### 3.2 消融实验与传统基线（宏 F1，3 种子均值）

| 实验组 | 宏 F1 | 参数量 | 结论 |
|--------|-------|--------|------|
| **CNN+BiLSTM 双分支（本文主模型）** | **0.9940 ± 0.0011** | 151k | 本文方案 |
| 去掉 CNN 分支（仅 BiLSTM） | 0.9966 ± 0.0003 | 96k | 与主模型持平（差异小于种子波动） |
| 去掉卷积与循环（纯 MLP） | 0.9795 ± 0.0033 | 172k | ↓1.5 个百分点 |
| 去掉 BiLSTM 分支（仅 CNN） | 0.9727 ± 0.0048 | 65k | **↓2.1 个百分点，时序分支是主力** |
| 逻辑回归 | 0.9739 | 9k | 传统基线中最强 |
| 随机森林 / 极端随机树 | 0.8767 / 0.8343 | 255k / 737k（树节点数） | 高维展平后明显劣于时序模型 |

**如实说明**：双分支混合模型与单独 BiLSTM 分支的差异小于随机种子波动，
即**时序分支是主要贡献者**；概率集成（7 个模型取平均）宏 F1 为 0.9964，同样只是与单分支持平。
但**窗口长度消融（见 3.3）给出了有价值的机理解释**：卷积分支的差距随窗口变长**单调收敛**，
说明它需要更长的上下文才能发挥作用 —— 我们把这条负面结论转化成了可验证的机理解释。

### 3.3 窗口长度消融（本轮新增，直接给出部署建议）

窗口长度 T 是本工程**最重要的超参数**——它同时决定精度与误报率（同一份数据、同一步长、25 epoch）：

| T | 混合模型宏 F1 | 仅 CNN 分支 | 仅 BiLSTM 分支 | 混合 − 最好单分支 | 误报（次/小时） |
|---|---|---|---|---|---|
| 10 | 0.9772 | 0.9415 | 0.9886 | −0.0114 | 28.31 |
| 16 | 0.9940 | 0.9670 | 0.9973 | −0.0033 | 9.22 |
| 24 | **0.9970** | 0.9813 | 0.9977 | **−0.0007** | **3.29** |

**三条可写进答辩的结论**：

1. **窗口越长越准**：宏 F1 从 0.9772（T=10）提升到 0.9970（T=24）；
2. **误报率随窗口长度断崖式下降**：28.31 → 3.29 次/小时（**降低 88%**）——
   这是部署侧最有价值的发现（多给模型一点上下文，运维少受 8 倍打扰）；
3. **CNN 分支的增益随窗口变长单调收敛**（−0.0114 → −0.0033 → −0.0007）：
   在 T=24 时混合模型与单分支的差距已小于随机种子波动，
   **印证了"卷积分支的价值需要更长窗口才能体现"这一假设**。
   这也把原先"CNN 分支没增益"的负面结论，变成了**有数据支撑的机理解释**。

> 代价与权衡：窗口越长，检测时延越大（T=24 意味着要等 24 条流记录才能出一次结论）。
> 部署时按业务的时延容忍度选择，并在报告中如实给出这条权衡曲线。
> **稳健性核对**：T=24 会出现窗口重叠（相邻窗口共享 19/24 条记录），
> 因此额外做了"决策步长加倍"的对照（T=24、step=12）：宏 F1 **0.9975**、误报 5.27 次/小时，**结论不变**。

### 3.4 分布漂移鲁棒性（`drift_strength=0.35`，模拟攻击工具换代/带宽变化）

| 模型 | 宏 F1（同分布） | 宏 F1（漂移集） | 退化 |
|------|-----------------|-----------------|------|
| **CNN+BiLSTM（主模型，3 种子）** | 0.9930 / 0.9956 / 0.9934 | 0.9934 / 0.9940 / 0.9918 | **−0.16% ~ +0.04%（基本不变）** |
| 仅 BiLSTM | 0.9964 | 0.9956 | −0.08% |
| 仅 CNN | 0.9670 | 0.9696 | +0.26% |
| 逻辑回归 | 0.9739 | 0.9739 | 0.00% |
| 随机森林 | 0.8767 | 0.7996 | **−7.7%** |
| 极端随机树 | 0.8343 | 0.7961 | **−3.8%** |

**在 T=16 的窗口下，时序深度模型对分布漂移几乎免疫（退化 ≤0.2%）**，而树模型仍退化 3.8%~7.7%。
这是"窗口化时序建模"最实用的价值：换个网络环境、换个攻击工具，模型不会突然失灵。

### 3.5 真实公开数据集验证（inSDN 衍生集，含诚实结论）

为避免"自己造的数据当然准"的质疑，我们另用一份**真实公开的 inSDN 数据集**做了独立验证：
343,889 条真实流记录 → 清洗去重后 **184,747 条**（删除 35% 完全重复行）× 65 维特征。

| 切分口径 | 多分类准确率 | 二分类 ROC-AUC | 误报（次/小时） |
|---|---|---|---|
| 分层随机切分 | 0.9998 | 1.0000 | — |
| **按会话分组切分**（同一 Flow ID 不跨子集） | **1.0000** | 1.0000 | 0.00 |
| 分组 + 近似重复去重（最严口径） | 0.9976 | 0.9996 | 0.51 |

**但我们必须把这个高分的真实原因说清楚**（这也是本工程方法学的一部分）：

| 诊断项 | 结果 |
|---|---|
| 测试样本到训练集的最近邻距离中位数（标准化空间） | 0.0004 |
| **距离 < 0.01（几乎完全相同）的测试样本占比** | **84.95%** |
| **1-最近邻分类器（纯记忆式基线）准确率** | **0.9985** |
| 单特征 + 单阈值（决策树桩）准确率 | 0.8051（最好单特征 0.8583） |

结论：该公开数据集**既冗余又高度可分**，接近满分的成绩主要反映数据本身，**不能用来区分模型优劣**。
因此我们**以自研的高难度仿真数据集作为主要评估基准**（随机森林仅 0.878、主模型 0.985），
并把公开数据集的结果定位为"验证流水线在真实数据上端到端可用"。
我们把这套诊断工具（切分口径对照 + 最近邻泄漏诊断 + 单特征基线）也留在了工程里，方便复用到其他数据集。

### 3.6 错误分析（模型错在哪里）

对 3,513 个测试窗口逐条分析（`python tools/error_analysis.py` → `results/error_analysis.md`）：

| 项目 | 结果 |
|---|---|
| 总错误 | 17 个（**错误率 0.48%**） |
| **漏报（攻击→正常）** | **0** —— 8 个类别里 7 类错误率为 0，唯一错误来自 Normal |
| 误报（正常→攻击） | 17 个（Normal 错误率 0.680%） |
| 主要混淆对 | Normal→BruteForce 9 次（52.9%）、Normal→DoS 4 次、Normal→Probe 3 次、Normal→WebAttack 1 次 |
| 置信度 | 错误样本异常概率中位数 0.844，正确样本 0.008 |
| 错例特征画像 | 错例的共同特征是**包长显著偏小**（Average Packet Size / Packet Length Mean 等比同类正确样本低约 0.4~0.5 个 z） |

**读法**：错误方向全部是"误报"而非"漏报"，对安全场景是好消息；
误报集中在"小包短连接"被误判为暴力破解/扫描——这与这两类攻击的机理（小包高频）天然重叠，
属于数据本身的模糊地带，也是下一步补样本/做特征工程的着力点。

### 3.7 检测工作点选择（误报可控，直接回应行业第一痛点）

2025 SANS 调查显示 **73% 的组织把"误报"列为威胁检测的第一大挑战**。
因此我们不做"固定阈值报一个 F1"，而是把三个旋钮放进同一框架全枚举
（`python tools/operating_point.py`，**无需重训**）：

| 阈值 | 确认窗口数 | 攻击片段召回 | 误报次数 | 误报/小时 | 平均检测时延 |
|---|---|---|---|---|---|
| 0.30 | 1 | 100% | 34 | 11.19 | 9.9 ms |
| 0.50 | 1 | 100% | 26 | 8.56 | 9.9 ms |
| 0.50 | 2 | 100% | 4 | 1.32 | 14.3 ms |
| **0.50（当前默认）** | **3** | **100%** | **2** | **0.66** | **18.1 ms** |
| 0.50 | 5 | 100% | 0 | **0.00** | 32.3 ms |
| 0.90 | 3 | 100% | 0 | **0.00** | 19.5 ms |

**结论**：**召回保持 100% 不变**，仅靠"连续确认 3 个窗口"就把误报从 8.56 降到 **0.66 次/小时（−92%）**，
代价是时延 +8 ms；要求零误报可选"阈值 0.90 + 确认 3"（19.5 ms）。
运维按自己的误报预算挑点即可 —— 这是本作品对"误报痛点"的直接回应，也是相对同类工作最实用的差异点。

### 3.8 推理性能基准（能不能真的接到控制器上）

CPU 单进程实测（`python tools/benchmark_latency.py`）：

| 推理路径 | 批量 | 逐窗口延迟 | 吞吐 | 折算流记录/秒 |
|---|---|---|---|---|
| Keras `predict()`（演示服务路径） | 1 | 49.98 ms（含 ~36 ms 固定包装开销） | 20 窗口/秒 | 60 |
| Keras `predict()` | 256 | 0.21 ms | 4,865 窗口/秒 | 14,595 |
| **直接调用推理图（生产路径）** | 1 | **p50 0.92 ms**（P95 1.52 ms） | 73 窗口/秒 | 219 |
| **直接调用推理图（生产路径）** | 256 | **0.022 ms** | **45,281 窗口/秒** | **135,843** |

**结论**：模型计算量极小（单窗口 0.92 ms），瓶颈是 Keras `predict()` 的固定调用开销（约 36 ms）；
**按控制器采集周期攒批推理即可消除**。按 10 秒采集周期算，单周期可处理约 136 万条流记录 ——
普通 CPU 即可覆盖中小型校园网/企业网，**无需 GPU**。

### 3.9 把指标翻译成运维语言：每天多少告警、要多少人工（`results/ops_impact.md`）

评委和运维真正在意的不是 F1，而是「值班室会不会被淹没」。下表由 `python tools/ops_impact.py` 生成
（误报率按 3.04 小时在线回放的**实测**值外推到天；真实告警按**每天 20 次攻击**的业务假设折算；
单条告警按 6 分钟排查、一个班次按 8 小时）：

| 工作点 | 误报/小时 | 误报/天 | **告警/天** | 误报占比 | **人工工时/天** | 平均时延 | 漏掉攻击/天 |
|---|---|---|---|---|---|---|---|
| 阈值 0.50 + 确认 **1**（不做确认） | 8.56 | 205.4 | 225.4 | 91.1% | **22.5 h**（≈2.8 个班次） | 9.9 ms | 0 |
| 阈值 0.50 + 确认 **3**（工程默认） | 0.66 | 15.8 | 35.8 | 44.1% | **3.58 h** | 18.1 ms | 0 |
| 阈值 0.90 + 确认 **2**（预算内最优） | 0.33 | 7.9 | 27.9 | 28.3% | **2.79 h** | 16.1 ms | 0 |
| 阈值 0.90 + 确认 **3**（零误报点） | 0.00 | 0.0 | 20.0 | 0.0% | **2.00 h** | 19.5 ms | 0 |

**三条可以直接讲给评委的结论**：

1. **不做「连续确认」的系统在 1× 流量下就已经超出值班人力**（22.5 人工小时/天 ≈ 2.8 个班次），
   也就是说**误报本身就会变成事故**；加上确认（3 个窗口）后降到 3.58 小时/天，占用一个班次的 45%，
   而**攻击片段召回没有任何下降**（都保持 100%）。这个几乎零成本的机制每天省下 **19 个人工小时**。
2. **响应量级差**：从攻击出现到报警平均 **18 毫秒**（P95 71 毫秒），对比人工巡检的分钟—小时级。
3. **容量预警线（诚实给出边界）**：误报量随决策窗口数线性增长，流量放大 10× 时人工占用会从 45% 升到 222%，
   因此**规模每上一个量级都必须重新标定工作点**——我们不声称"无限流量下都够用"，
   这张表本身就是给容量规划用的预警线。

### 3.10 控制器原生字段口径：字段不够时，代价是多少？（`results/summary_sdn_ctrl.md`）

上线前最难回答的问题之一是：「你的模型用了 84 列 CICFlowMeter 特征，**真实 SDN 控制器取不到这些字段怎么办**」。
本工程把这条路也走通了：用**只有 OpenFlow 流表统计能提供的 17 列**（`packet_count`/`byte_count`/
`flow_duration_sec|nsec`/`tp_src`/`tp_dst`/`ip_proto`/`flags`/各类速率……，与仓库 Ryu 采集脚本同款字段）
重新生成数据、重新训练、重新评估：

| 口径 | 特征数 | 宏 F1 | 二分类 F1 | ROC-AUC | TPR@1%FPR | 片段召回 | 平均时延 | 误报/小时（各口径推荐点） |
|---|---|---|---|---|---|---|---|---|
| 完整流特征（`insdn`，84 列） | 71 | **0.9940** | 0.9918 | 0.9999 | 1.0000 | 100% | 18.4 ms | 0.55（阈值 0.50 + 确认 3） |
| **控制器原生字段（`sdn`，17 列）** | 17 | 0.8441 | 0.8533 | 0.9951 | 0.9151 | **100%** | 40.6 ms | 0.66（阈值 **0.99** + 确认 5） |

**这个结论比"指标更高"更有价值**，因为它量化的是一条真实的上线边界：

* 只用控制器原生字段，**攻击片段召回仍然是 100%**（该发现的都发现了），但**工作点必须大幅收紧**
  （阈值 0.50 → 0.99、确认 3 → 5），代价是**检测时延从 18 ms 涨到 41 ms**，且窗口级宏 F1 从 0.994 掉到 0.844；
* 换句话说，**字段缺口转化为"工作点代价"而不是"功能失效"** —— 这决定了没有探针的纯 SDN 环境里
  这套系统能用到什么程度、以及该优先补哪几类字段；
* 想同时拿到高精度与低时延，就必须在控制器侧补齐**双向包间隔/标志位统计**这类字段
  （完整口径相对原生口径多出的正是这些）。

两个口径都已封装进同一个服务，一条参数即可切换（`--processed-dir` + `--model-tag`），
**且服务与大屏会自动同步口径**，不会出现"页面显示的模型"和"实际判定的模型"不是同一个的事故。

### 3.11 控制平面闭环实测：这套东西真的能跑（`results/e2e_controller_report.md`）

`tools/controller_simulator.py` 在**没有 Ryu 的机器上**扮演控制器，走完整条链路
（流记录 → `POST /api/detect` → 告警 → 执行处置动作 → 写审计台账），实测：

| 指标 | 实测值 |
|---|---|
| 回放规模 | 3,000 条流 / 50 条一批 / 共 60 批 |
| 吞吐 | **1,364~1,918 条流/秒**（多次运行区间，中位约 1,650） |
| 判定时延 | **p50 29.8 ms / p95 44.7 ms / p99 45.7 ms**（剔除首批预热） |
| 首批预热 | 约 0.5 s —— TensorFlow 计算图构建的**一次性**开销，真实部署里只发生一次 |
| 端到端总耗时 | 1.6~2.2 s（含 HTTP 与策略下发） |
| 告警 | 235 条确认告警，其中 **228 条命中真实攻击、7 条误报** |
| 处置 | 全部按 `block` 策略正确执行（策略经 `/api/policy` 热更新，`dry_run=false`） |
| 可追溯性 | 每条告警写入 `results/audit_alerts.jsonl`（时间/源 IP/类别/置信度/动作/触发窗口/覆盖行区间） |

> 时延分位给出**两个口径**：含首批预热时 p99 会被预热拉到 200 ms 以上，
> 看起来像"服务不稳定"；剔除后 p99 仅 45.7 ms。我们两个数都列出来并说明原因，
> 而不是只挑好看的那个报。

对比优化前：**逐条调用 `predict()` 时 p50 为 1,261 ms（32 条流/秒）**，改成"批内合并 + 直接调用推理图"
后降到 **30 ms（1,364~1,918 条流/秒）**，**提速约 43~60 倍**。这说明在线部署的关键不是模型本身，
而是**把推理调用攒成批**这一层工程实现。

> 诚实声明：`integrations/ryu_guard.py` 是按 Ryu 官方 API 写好的适配层，**本机没有 Ryu/OpenFlow 交换机，
> 因此未在真实交换机上实跑**；上面这份报告验证的是**控制器↔检测服务之间的接口与处置逻辑**。
>
> 但"没装 Ryu 就跑不了"**不等于"没法验证"**：`tests/test_ryu_guard.py` 用桩件替代 `ryu` 模块、
> **真的调用适配层核心逻辑**，锁死 25 项接口契约与安全默认值（含「记录字段必须覆盖模型全部 17 个特征名」
> 这条硬接口契约）。这个测试当场抓出并修掉了两处**「账实不符」**缺陷：
> `block` 只记账不下发规则、`throttle` 只建 Meter 却没把流表项挂上去（**只建 Meter 是不限速的**）——
> 它们是最危险的一类问题：台账显示"已处置"，交换机上其实什么都没发生。

### 3.12 跨域适用边界：我们主动做的一次"失败实验"（`results/cross_dataset_report.md`）

把自研数据集上训练好的模型**零样本**直接拿去推理真实 inSDN（71 维特征按语义 100% 映射成功，
全程只做推理、不用真实数据训练或重拟合任何参数），再逐级加校准：

| 设定 | 需要标注 | ROC-AUC | 二分类 F1 | 1% 误报预算下的召回 |
|---|---|---|---|---|
| 同域（有目标域数据，按正常流程训练） | 全部 | 0.9996 | 0.9986 | —（准确率 0.9976） |
| 零样本跨域（自研 → 真实，直接推理） | 0 | 0.6697 | 0.5629 | 0.0006 |
| 只重新拟合标准化器（无需标签） | 0 | **0.4742** | — | 0.0002 |
| +500 个标注窗口微调分类头（3.1 s） | 500 | 0.7034 | 0.5965 | **0.4257** |
| +解冻主干再训 2 epoch（共 6.6 s） | 500 | 0.7657 | 0.6150 | **0.4453** |

**三条结论（都写进了报告，没有藏）**：

1. **零样本跨域不可用**（F1 0.5629、误报率 21%），而且**只重拟合标准化器会把 AUC 从 0.6697 打到 0.4742** ——
   零样本那点排序能力有相当部分来自"漂移幅度本身"造成的假信号（攻击行偏离合成分布更远，被误打误撞排到前面），
   把量纲拉回目标域口径就消失了。**这条反直觉结论的实用价值是：跨域 AUC 高不能被当作"模型还能用"的证据。**
2. **真正有效的是少量目标域标注**：500 个窗口、3 秒微调分类头，召回由 0.0006 提到 0.4257；
   再解冻主干 6.6 秒提到 0.4453 —— 仍远低于同域的 0.9986。逐特征漂移诊断指出根因是
   **采集口径差异**（CICFlowMeter 的流切分/超时/子流定义）而非模型结构：重定标后
   "正常流量像不像训练数据"确实修好了（|z-shift| 均值 0.4956→0.2089、超 1σ 特征 7/71→1/71），
   但"攻击长什么样"修不了（攻击行仍 |z| 均值 0.275、最大 2.94）。
3. **正确的下一步不是继续调模型，而是用目标域统计量反向标定生成器参数（域随机化）** ——
   本作品生成器的均值/方差/重尾参数都是显式可调的，这正是把它做成参数化工具的价值。
   另需说明：该公开数据的窗口并非真实时序（按攻击类型分块拼接发布），
   故上表数值应视为"**窗口级分类**"的上界参考，**不等于在线检测召回率**。

> 我们说这件事，是因为**一个能上线的东西必须知道自己在什么条件下会失效**。
> 同时请注意对照：同一个模型与流水线，在**有目标域数据**时（同域训练/评估）在该真实数据集上
> 可达 0.9976–1.0000（见 3.5），所以失效的原因是域漂移与采集口径，而不是模型或工程本身。
>
> **复现说明**：`python tools/cross_dataset.py` 需要真实数据集 `data/real/insdn/Dataset.csv`。
> 该数据集未标注许可证，依竞赛规则**不再分发**（已 gitignore），因此本实验在仓库里**默认不可一键复现**——
> 完整数值与逐特征明细已固化在 `results/cross_dataset_report.md` 与 `results/cross_dataset.json` 中，
> 拿到同源数据后 `python tools/cross_dataset.py` 一条命令即可重跑（约 42 秒）。

### 3.13 未知攻击（开集）检测：训练时没见过的新型攻击会怎样？（`results/openset_report.md`）

前 8 类都是"已知"的。真实网络里最要命的问题是：**出现训练时从未见过的新型攻击时，系统会不会盲目地
把它硬塞进某个已知类别、还给出很高置信度？** 我们做了开集实验：**把整类攻击从训练/验证中拿掉**
（留出 U2R、留出 Botnet 两个场景 × 3 个种子），测试集里保留该类作为"未知攻击"，
用只在已知类上标定的阈值来评估。

| 留出场景 | 不做拒识时会怎样（**最危险的一组数据**） | 未知检出率 UDR | 已知类宏 F1 代价 |
|---|---|---|---|
| **留出 U2R** | 100% 被安上已知标签：**84% 判成 WebAttack**、13% 判成 DoS，平均置信度 0.82、42% 置信度 ≥0.9 | 1% 误报预算 **69.8%**；0.1% 预算 30.2%（energy 分数） | 0.9931 → 0.9881（−0.5 pt） |
| **留出 Botnet** | 100% 被安上已知标签：**96% 判成 Normal** —— 意味着攻击**连告警都不会触发**，比错报成别的攻击更危险 | 1% 预算 **44.3%**；0.1% 预算 **0.9%**（energy 分数） | 0.9931 → 0.9942（**无代价**） |

**三条结论（都如实写进报告）**：

1. **不拒识的后果是"自信地把新攻击叫成老朋友"**：42% / 74% 的未知窗口被以 ≥0.9 的置信度错判。
   运维会按错误的攻击类型去处置，这比漏报更容易造成误判性事故。
2. **拒识有效，但强烈依赖"未知攻击与已知/正常流量有多像"**：机理独特的 U2R 在 1% 预算下能捞出 70%；
   而与正常流量形态接近的 Botnet（C2 心跳、低速率、长连接）**1% 预算下只能捞出 44%，0.1% 预算下几乎失效（0.9%）**。
   **AUROC 会骗人**——三个 OOD 分数的跨场景 AUROC 都在 0.978 左右，但尾部（低误报预算）表现差了一个数量级。
3. **拒识几乎不伤已知类**：加拒识后已知类宏 F1 反而略升（0.9881→0.9928 / 0.9942→0.9946），
   因为被误拒的已知攻击仍会告警（只是标签变成"未知"）。**所以正确的用法是叠加而非替代**：
   二分类头负责"是不是攻击"，OOD 分数负责"是不是已知类型"，未知告警进人工研判队列，
   确认后回流训练集，形成「未知 → 已知」的闭环。

**这条结论已经落成可用的运行时旋钮**：`tools/openset_calibrate.py` 在**正常窗口**上按误报预算标定阈值
（默认 `entropy`，1% 预算 → 0.3914；此时正常被判未知 1.00%、已知攻击被判未知 0.30%），
再把 `unknown_threshold` 通过 `/api/policy` 热更新进服务——开启后熵超阈值的窗口显示为
`Unknown（未知形态）`，**照常告警与处置**，只是不再声称具体类别；`/metrics` 同步暴露
`sdn_ids_unknown_windows_total`（未知占比本身就是一条免费的漂移指标）。

> 部署建议（报告 8.1 节）：优先用能量分数 `-logsumexp(logits)`；阈值在生产环境的正常流量上取分位数
> （1% 预算取 99 分位）；**未知告警比例本身就是一条免费的漂移指标**，突然升高通常意味着新攻击出现。
> 诚实边界：留出类样本量小（42 / 73 个窗口），且"未知"来自同一生成器，与真实新型攻击仍有差距。

## 5. 数据：为什么可以自己生成，以及怎么换成真实数据

### 5.1 两种输出格式（都经过列名核对）

| schema | 列数 | 与谁对齐 | 用途 |
|--------|------|----------|------|
| `insdn`（默认） | 84 列 | 公开数据集 **inSDN / CIC-IDS2017**（CICFlowMeter 输出）列名逐字一致 | 与原始 demo 期望的格式对齐；方便横向对比公开数据集结果 |
| `sdn` | 22 列（+1 列多分类标注） | 本仓库 `collect_normal_traffic.py` / `collect_ddos_traffic.py`（Ryu 控制器采集 OpenFlow 流表统计）的输出 | 与自己的 SDN 实验床无缝衔接 |

```bash
python run_all.py --set schema=sdn        # 换成 Ryu 采集脚本同款 22 列格式
```

### 5.2 8 类流量（与 inSDN 类别体系对齐）

| 类别 | 机理建模要点（为什么模型能学到） |
|------|----------------------------------|
| Normal | HTTP / 大文件传输 / DNS / ICMP / UDP 流的混合，量级跨度大 |
| DDoS | 多源、**超高包速率（可达 1e4 pkt/s）**、极短持续、几乎无反向包 |
| DoS | 单源、速率中等、**持续时间长**；Slowloris 甚至几百秒的极低速率长连接 |
| Probe | 端口扫描：单流 1~3 个包、时长毫秒级、SYN/RST 标志、目标端口随机 |
| BruteForce | SSH/FTP 反复认证：等间隔小包往返、连接数中等 |
| WebAttack | HTTP 注入载荷：前向包偏大、PSH 比例高 |
| Botnet | C2 心跳：**到达间隔极其规律**（正则化系数极低）、速率极低、连接超长 |
| U2R | 极少见：载荷异常、标志位组合异常（URG/ECE/CWE 同时出现） |

生成器是**先生成物理事实、再渲染成数据集列**的：包数、字节数、时长、活跃/空闲时间、
标志位计数、到达间隔统计之间互相自洽（例如 `Flow Packets/s = 总包数 / 时长`、
`Packet Length Mean = 总字节 / 总包数`），不会出现"随机撒点导致的物理上不可能的样本"。

同时内置了**可控的难度旋钮**，保证指标不是虚高：

| 配置项 | 含义 |
|--------|------|
| `overlap_ratio` | 每类中与"最易混淆类"做几何混合的困难样本比例（默认 15%） |
| `label_noise` | 标注噪声比例（默认 1%） |
| `feature_noise` | 量测噪声强度（默认 5%） |
| `drift_strength` | 额外生成一个**分布漂移测试集**（鲁棒性实验） |

## 6. 方法

### 6.1 网络结构

```
输入 (T, F)：T 条连续流记录 × F 维流特征（默认 T=10）
  │
  ├─ CNN 分支：Conv1D(64,k=3,膨胀率1) → BN → ReLU → Conv1D(128,k=3,膨胀率2) → BN → ReLU
  │            作用：沿时间轴提取"相邻若干条流"的局部组合模式（突发 SYN、等间隔心跳）
  │            ★ 用膨胀卷积而非池化，避免把 10 个时间步压成 2 个
  │
  ├─ BiLSTM 分支：BiLSTM(64, return_sequences=True)
  │            作用：直接在原始窗口上做双向时序建模，抓整段演化趋势
  │
  ├─ 两条分支各自池化后拼接（CNN 分支全局最大池化 + 时序分支注意力池化）
  │            ★ 并行双分支，比"CNN 输出再喂 LSTM"的串行做法更稳（见 docs/02 消融讨论）
  │
  └─ 双头输出
       ├─ 多分类头 softmax(8)：认得出是哪种攻击
       └─ 二分类头 sigmoid(1)：直接回答"正常 / 异常"
     损失 = CE(多分类) + 0.3 × BCE(二分类)   ← 多任务联合训练
```

### 6.2 数据切分（这里最容易翻车，也最能体现工程严谨性）

```
时间轴 ──────────────────────────────────────────────────────────────▶
        │  训练集 60%  │purge│ 验证集 15% │purge│   测试集 25%   │
        └──────────────┘     └────────────┘     └───────────────┘
   * 严格按时间顺序切分（网络流是时序数据，随机切分 = 数据泄漏）
   * 边界留 purge 间隙，滑窗不跨集
   * StandardScaler 只在训练集 fit，再 transform 验证/测试集
   * 验证集用于早停与调参，测试集只在最终评估时用一次
```

### 6.3 评估体系（三套指标一起看）

1. **多分类**：accuracy、macro/weighted P-R-F1、逐类明细、混淆矩阵、Kappa、Top-2、macro AUC(OvR)
2. **二分类异常检测**：ROC-AUC、PR-AUC、MCC、最优阈值下的 F1、**TPR@FPR=1%/0.1%**（安全场景最常用的工作点）
3. **在线告警级**：在连续测试流上滚动取窗，统计
   - **检测时延**：攻击开始 → 第一条告警（均值 / 中位数 / P95，秒）
   - **误报率**：次/小时（工程上看这个，比 FPR 比例更直观）
   - **攻击片段召回率**：有多少个攻击片段被报出来、漏报几个

# 主实验（默认配置：inSDN schema + 滑窗时序 + CNN-BiLSTM + 双头）

# 换 Ryu 采集脚本同款 22 列 schema
python run_all.py --set schema=sdn

演示大屏与报告都依据这个指针取产物，不会出现"演示的是 A 模型、指标是 B 模型"的情况。

## 8. 可视化演示大屏 + 在线检测服务

```bash
python app/app.py                 # http://127.0.0.1:5000
python app/app.py --port 8000
# 控制器原生字段口径（服务与大屏一起切换）
python app/app.py --processed-dir data/processed_sdn --model-tag sdn_ctrl
```

界面功能（现场答辩用）：

- **实时检测曲线**：异常概率随时间变化，叠加"真实攻击区间"与"告警区间"，一眼看出漏报/误报
- **当前窗口判定**：大号风险值 + 8 类概率条，实时展示模型"在想什么"
- **一键注入攻击**：点一下就跳到测试流里真实的攻击片段起点，看模型多快报警
- **流量流水表**：逐条流记录展示关键特征 + 真实标签 + 模型判定（人工可对照）
- **告警日志**：记录每一次告警的时刻、判定类别、概率、是否误报
- **实验指标与图表**：直接读取 `results/` 下的指标与图片，可点击放大

同一个进程还对外提供**在线检测接口**（控制器直接调用，不是给页面用的）：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/detect` | 推一批流记录 → 逐条判定 + 新告警 + 处置建议（**控制器调这个**） |
| GET | `/api/alerts` | 告警审计台账（时间/源 IP/类别/置信度/动作/触发窗口） |
| GET/POST | `/api/policy` | 查询/热更新策略：阈值、确认窗口数、动作、白名单、演练模式（**无需重启**） |
| GET | `/api/stats` | 吞吐、时延分位、各类告警计数（可观测） |
| GET | `/metrics` | Prometheus 文本格式，直接接进现有监控 |

三个工程上的取舍（都可讲）：

1. **演示不依赖 TensorFlow**：推理在实验阶段就缓存成"窗口级预测"，演示服务只做回放，
   因此在评委电脑上没装 TF 也能跑；断网也能跑（前端零 CDN，图表全部原生 canvas 绘制）。
   （注意：`/api/detect` 这条在线链路需要 TensorFlow；两条路径互不影响。）
2. **回放的是留出测试集**：不是编好的动画，预测结果与 `results/metrics_*.json` 同源，**演示与论文数字一致**。
3. **"注入攻击"是诚实的**：只是把播放位置跳到真实攻击片段起点，检测时延由模型自己决定。

## 9. 与原 demo 的差异（摘要）

| 维度 | 原 demo | 本工程 |
|------|---------|--------|
| 数据来源 | 硬编码别人机器上的路径 | 自带生成器 / 一键切换真实数据集 |
| 特征选择 | `data[:, 0:77]` 硬编码（还混入了行号列、漏掉了一个特征） | 按列名自动识别 |
| 标准化 | 全量数据 fit（泄漏） | 只在训练集 fit |
| 切分 | 随机切分 + 测试集当验证集（泄漏） | 时序切分 + purge 间隙 + 独立验证集 |
| 损失 | 二分类损失训多分类 one-hot | 多分类 CE + 二分类 BCE 双头 |
| 早停/学习率 | 监控训练损失；min_lr > 初始 lr（永不衰减） | 监控 val_loss + restore_best + 正确的 lr 调度 |
| 时序建模 | 硬切假时间步 | 真实滑动窗口 (T,F) |
| AUC 计算 | 硬标签算 AUC（口径错误） | 概率矩阵 + OvR 宏平均 |
| 类别不平衡 | 不处理 | 逆频类别加权 |
| 可复现 | 无种子、不保存 scaler/编码器 | 全固定 + 全部落盘 |
| 评估维度 | 离线静态指标 | 多分类 + 二分类 + 在线告警级 + 运维工作量 |
| 上线形态 | 只能手动跑脚本看结果 | 常驻检测服务 + 控制器对接 + 审计台账 + 监控指标 |
| 处置能力 | 无 | 策略化 observe/throttle/block + 白名单 + 演练模式 + 自动过期 |
| 演示 | 无 | 实时检测大屏 |

## 10. 常见问题

**Q：一定要装 TensorFlow 吗？**
训练与推理需要；但 `tools/smoke_test.py`（数据链路自检）和演示大屏（读缓存预测）都不需要。

**Q：没有 GPU，训练要多久？**
默认配置（约 6~7 万条流记录、T=10 窗口、约 4 万训练窗口、40 epoch，含早停）
在 8 核 CPU 上大约几十分钟。想更快就 `--smoke` 或 `--set scale=0.4`。

**Q：图里的中文变成方块？**
`src/utils.py` 会自动查找 微软雅黑/黑体/苹方/文泉驿 等字体；都没有时会自动**回退成英文标注**，
不会报错。也可以手动把任意 `.ttf` 放进系统字体目录后重跑。

**Q：Windows 控制台中文乱码？**
`src/utils.py` 会把 stdout 切到 UTF-8；若仍乱码，运行前执行 `chcp 65001`。

**Q：想换个数据规模？**
`--set scale=0.5`（数据量）、`--set window_size=16`（窗口）、`--epochs 60`（轮数）。

**Q：想复现某个结果？**
配置里固定了 `seed`，并写入 `artifacts/<tag>/config_used.json`；使用同一份配置 + 同一版本依赖即可复现。
