## 一、作品概述

### 1.1 背景与问题

SDN（软件定义网络）把控制平面集中到控制器上，控制器天然掌握全网流表统计。这带来一个机会：
**不需要在每台主机部署探针，就能在网络中枢直接观察流量级攻击**——DDoS 洪泛、端口扫描、
暴力破解、僵尸网络心跳等。

但现实中的落地障碍有三层：

1. **识别仍靠人工规则**：运维人员靠阈值与经验规则判断异常，规则更新滞后于攻击手法变化；
2. **已有研究型成果不可用**：公开的算法 demo 多数存在数据泄漏（随机切分连续流量）、
   评估口径错误（在多分类任务上用二分类损失、用硬标签计算 AUC），指标虚高且无法复现；
3. **不可复现 = 不可信**：数据集路径硬编码、随机种子不固定、标准化器与标签编码器不落盘，
   换一台机器或换一份数据就失效，评审与工程团队都无法验证。

**目标用户**：校园网/企业网中负责 SDN 控制器运维的网络与安全工程师。
**使用场景**：控制器按固定周期拉取流表统计，形成连续流记录序列，由检测服务实时判定异常并告警。
**本作品要解决的具体问题**：把"一份跑不起来的研究型 demo"变成"**一条命令可复现、可现场演示、
可被他人复用**的异常流量检测开源工程"，并把每一处数据泄漏与评估错误修掉、留下证据。

### 1.2 目标、参赛方向与作品形态

- **参赛方向**：**开源项目改进与生态贡献**（同时体现"开源赋能的 AI 应用创新"）。
  作品围绕上游研究型 demo 开展**二次开发、功能增强、测试用例与文档建设、问题修复**，
  并形成可运行、可演示、可复验的软件原型。
- **作品形态**：Python 工程 + 命令行工具链 + **常驻在线检测服务**（可被 SDN 控制器调用）+
  **Ryu 控制器适配层** + 本地 Web 演示大屏（离线可用）。
- **核心功能**：
  1. 自研仿真流量生成器（不依赖任何外部数据集即可产出训练数据）；
  2. CNN + BiLSTM 双分支异常检测模型（多任务双头输出）；
  3. 三套评估口径 + 运维工作量换算 + 12 类实验图表自动生成；
  4. **在线检测服务**：`POST /api/detect` 在线判定、告警连续确认、`observe/throttle/block` 处置策略、
     白名单、演练模式、JSONL 审计台账、Prometheus `/metrics`、策略热更新；
  5. **控制器对接**：`integrations/ryu_guard.py` 从 OpenFlow 流表统计取字段 → 判定 → 下发限速/阻断；
  6. 实时检测演示大屏（回放真实留出数据 + 一键注入攻击）；
  7. 交付验收自检（116 项，含在线接口实调）与完整文档（含 `DEPLOYMENT.md`）。

## 二、需求分析与总体方案

### 2.1 需求分析

**先说结论：安全运营最痛的不是"检不出"，而是"报太多"。**

2025 年 SANS 检测与响应调查显示（[SANS 2025 Detection & Response Survey](https://www.stamus-networks.com/blog/what-the-2025-sans-detection-response-survey-reveals-false-positives-alert-fatigue-are-worsening)）：

- **73% 的组织把"误报"列为威胁检测的第一大挑战**，且相比上一年显著上升；
- **超过 60%** 的受访者频繁或非常频繁地遇到误报，"非常频繁"的比例一年内由 13% 涨到 20%；
- 高噪声环境会掩盖真实威胁、加剧人员流失——**告警疲劳本身就是安全风险**。

这直接决定了本作品的需求优先级（与"只追求准确率"的常见做法不同）：

| # | 需求 | 依据 | 本作品的应对 |
|---|---|---|---|
| ① | **误报可控**：能按运维的误报预算选择工作点 | 上面 SANS 数据：误报是第一痛点 | 提出**检测工作点三旋钮**（窗口长度 × 判定阈值 × 告警确认次数），给出 Pareto 表与图，实测可把误报由 8.56 压到 **0.66 次/小时**且召回保持 100% |
| ② | 漏报要低：攻击片段不能整段漏掉 | 安全事件的后果不对称 | 攻击片段召回 **100%（24/24）**，逐类错误率中攻击类漏报为 **0** |
| ③ | 时延可接受：告警要"来得及处置" | 需要与控制器采集周期匹配 | 平均检测时延 18.1 ms（流时间），单窗口推理 p50 **0.92 ms**（CPU） |
| ④ | 能落地：普通 CPU 就能跑、能接到控制器上 | 校园网/企业网通常没有 GPU | 性能基准：批量推理 **4.5 万窗口/秒**（≈13.6 万条流/秒）；**控制平面闭环实测 1,364~1,918 条流/秒、判定 p50 约 30 ms**，无需 GPU |
| ⑤ | **误报要换算成人力，而不只是次数** | "次/小时"运维听不懂，人力预算才听得懂 | `tools/ops_impact.py`：推荐工作点 **≈36 条告警/天、3.6 人工小时/天、漏报 0**；不做确认则需 **22.5 小时/天**（约 2.8 个班次） |
| ⑥ | **要能处置，而不只是报警** | 只报警的系统在 SDN 里等于没闭环 | 处置策略 `observe/throttle/block` + 白名单 + 演练模式 + 有效期自动过期 + 审计台账；Ryu 适配层可直接下发 OpenFlow 规则 |
| ⑦ | 可复现、可复用：别人能验证与二次开发 | 公开研究成果普遍不可复现 | 一条命令复现 + 116 项验收自检（含接口实调）+ Apache-2.0 开源 |

**现有做法与痛点**：

| 现状做法 | 痛点 | 本作品的应对 |
|---|---|---|
| 人工阈值规则 | 阈值靠经验；攻击手法变化后失效 | 用模型从流统计量学习判别边界，且阈值/窗口/确认次数都可现场调 |
| 传统 IDS（Snort/Suricata/Zeek） | 依赖签名与人工规则，未知攻击与加密流量效果差；规则维护成本高 | 从**流统计量**学习判别边界，不依赖载荷，天然适配加密流量 |
| 论文式 demo | 换机器跑不起来；指标不可复现 | 一条命令复现 + 固定随机种子 + 产物全落盘 |
| 只报准确率/F1 | 无法回答"上线后多久报警、每小时误报几次" | 增加在线告警级指标与工作点选择工具 |
| 自造数据评估 | 数据过于简单，指标虚高 | 内置难度旋钮；并用公开真实数据集独立验证（并主动诊断其 85% 近似重复问题） |

**需求优先级**：① 能跑起来并且能复现（否则一切无意义）→ ② **误报可控、漏报要低** →
③ 时延与算力可接受、能真正落地 → ④ 能演示、能解释（运维看得懂）→ ⑤ 能被别人复用。

**输入输出**：输入为逐条流记录（时间有序，含统计特征与标签）；输出为每条记录所属攻击类型、

## 三、AI 技术与开源及第三方资源选择

### 3.1 AI 技术作用

| AI 技术 | 在作品中的具体作用 | 为什么必须用 AI | 如何验证输出 |
|---|---|---|---|
| CNN（一维膨胀卷积） | 从"相邻若干条流"中提取局部组合模式（突发 SYN、等间隔心跳） | 攻击常表现为**多步组合模式**，单条流不可判 | 消融实验（去掉时序分支指标下降） |
| BiLSTM | 对窗口内的时间依赖双向建模（攻击的起始—持续—演化） | 攻击有演化过程，单向或无序模型抓不住 | 消融实验 + 在线片段召回率 |
| 注意力池化 | 对时间步加权，输出"哪几条流最可疑"的热力图 | 运维需要告警依据，不能只给一个概率 | 注意力热力图 + 隐患样本人工核对 |
| 多任务双头 | 同时输出攻击类型（多分类）与正常/异常（二分类） | 业务既要"是不是攻击"也要"是什么攻击"；联合训练可互相正则 | 两套指标分别报告 |
| 类别加权 | 逆频加权，缓解攻击样本稀少 | 不加权模型会退化为"全判正常" | 逐类召回率明细表 |

### 3.2 开源及第三方资源选择

完整清单见附件《开源及第三方资源使用清单》。选型依据：

- **TensorFlow/Keras**：生态成熟、CPU 版即可训练本规模模型；模型可保存为 `.keras` 便于部署；
- **scikit-learn**：评估指标口径标准、便于引入传统机器学习基线做对照；
- **pandas/NumPy**：真实数据集清洗与窗口构造；
- **matplotlib/seaborn**：论文级图表；
- **Flask**：演示服务零前端依赖，**完全离线可用**（比赛现场无网络也能演示）。

**自主开发边界**：所有业务代码（生成器、清洗与滑窗、模型构建与训练、评估体系、
可视化、演示服务、工具链、文档）均为团队自主编写；第三方库仅作为依赖被调用，未修改其源码。

### 3.3 融合方式

作品不是"调用通用模型接口"或"简单部署现有项目"：**AI 模型是核心功能本身**（流量的判别边界由模型学习），
而开源生态提供了训练框架、评估工具与可视化基础。相较上游 demo 的实质改进包括：

1. **建模方式**：由"把 1280 维特征硬切成 10 个假时间步"改为**真实滑动窗口**；
2. **评测方法**：由"随机切分 + 测试集当验证集 + 硬标签算 AUC"改为
   **时序切分 + purge 间隙 + 独立验证集 + 概率矩阵 OvR 宏平均**；
3. **数据来源**：由"硬编码他人机器上的数据集路径"改为**自带生成器 + 一键接入真实公开数据**；
4. **工程能力**：新增一键复现流水线、116 项验收自检、12 类图表、离线演示大屏与 34 个工具脚本（含交付验收自检）。

### 4.2 关键实现

**（1）滑动窗口与真正的时序建模。** 输入为 `(T, F)`：T 条连续流记录 × F 维流特征。
窗口只在"片段内部"构建，跨片段（标签混合）窗口被丢弃，避免把攻击起始点混进正常窗口。

**（2）双分支并行结构。** CNN 分支使用**膨胀卷积**而非池化——因为池化会把 10 个时间步压缩成 2 个，
使 BiLSTM 的时序建模名存实亡（这是开发过程中真实踩到的坑，串行结构下混合模型反而跑不过单分支）。
两分支各自池化后拼接，交给分类头自行权衡。

**（3）多任务双头损失。** `L = CE(多分类) + 0.3 × BCE(二分类)`。
多分类头用 `sparse_categorical_crossentropy`（整数标签），二分类头用 `binary_crossentropy`，
并配合逆频类别权重（通过 `sample_weight` 适配多头模型）。

**（4）防泄漏的切分与预处理。** 支持两种切分：
- **时序切分**（默认）：按时间顺序切分训练/验证/测试，边界留 purge 间隙；
- **按组切分**：对"分块发布"的公开数据集（正常块+攻击块）或需防会话泄漏的场景，
  按会话（Flow ID）分组切分，同组数据只能进同一子集。
标准化器**只在训练集拟合**。

**（5）数据生成器的物理量自洽。** 生成器先产生"流记录的物理事实"（包数、字节数、时长、
标志位、到达间隔、活跃/空闲时间），再渲染成数据集列，因此
`Flow Packets/s = 总包数 / 时长`、`平均包长 = 总字节 / 总包数` 等关系恒成立
（验收自检实测相对误差 0.00e+00）。

**（6）难度可控。** 生成器提供三个旋钮：`overlap_ratio`（与最易混类混合的困难样本比例）、
`stealth_ratio/stealth_mix`（隐蔽型攻击片段——片段内混入大量正常样貌的流，单条流不可判、
必须靠窗口聚合识别）、`label_noise`（标注噪声）。

**（7）在线检测服务：把模型包成可被调用的系统。** `src/service.py` 实现
`DetectionService`：维护长度 = 窗口长度 T 的滑窗缓冲 → 按在线步长攒批推理 → 阈值判定 →
**连续 N 个窗口超阈值才确认告警**（N 可热更新）→ 按策略给出 `observe/throttle/block` 建议 →
白名单过滤 → 演练模式（只记录不改流表）→ 每条告警写 JSONL 审计台账。
服务同时暴露 `/api/policy`（阈值、确认次数、动作、白名单、演练模式**无需重启即可热更新**）、
`/api/stats`（吞吐/时延分位）与 `/metrics`（Prometheus 文本格式，可直接接进现有监控）。

**（8）批量推理优化（约 43~60 倍提速的来源）。** 最初实现每条流记录调用一次
`model.predict()`，实测 p50 **1,261 ms**、仅 32 条流/秒——瓶颈是 Keras `predict()` 每次约 36 ms 的
固定包装开销，而非模型计算量。改进为**批内合并 + 直接调用推理图**
（`tf.function` 包装的训练图直接调用，失败时回退 `keras_predict`），
实测 p50 **约 30 ms**、**1,364~1,918 条流/秒**，端到端提速**约 43~60 倍**。
这条经验对任何"DL 模型上线"的场景都适用：**先解决调用开销，再谈模型压缩**。

**（9）模型与预处理口径的一致性校验（上线安全阀）。** `artifacts/` 下同时存在多种特征口径的
模型（完整流特征 71 维、控制器原生字段 17 维、真实数据 65 维）。服务启动时不再"取最新一个模型"，
而是按**优先级 + 输入形状校验**逐个尝试：形状与预处理产物不符就跳过，
全部不符时**直接拒绝启动并打印已尝试的候选清单**——宁可服务起不来，也不给错误判定。
这条规则是在开发中发现"17 维模型配上 71 维预处理产物"导致运行时报
`expected shape=(None,16,71), found (15,16,17)` 之后加入的。

9. **（本轮）同一份 `artifacts/` 下并存多种特征口径的模型后，服务"取最新一个模型"会配上不匹配的

10. **（本轮）现场演示"注入攻击"时发现注入到了只有 1 条流的碎片片段上、看起来像漏报** →

**（2）消融与基线对比（宏平均 F1，3 种子均值）**

| 实验组 | 宏 F1 | 参数量 | 结论 |
|---|---|---|---|
| CNN+BiLSTM 双分支（本作品主模型） | **0.9940 ± 0.0011** | 151k | 主方案 |
| 仅 BiLSTM 分支 | 0.9966 ± 0.0003 | 96k | **与主模型持平（差异小于种子波动）** |
| 仅全连接（MLP） | 0.9795 ± 0.0033 | 172k | ↓1.5 pt |
| 仅 CNN 分支 | 0.9727 ± 0.0048 | 65k | **↓2.1 pt，时序分支是主要贡献者** |
| 晚融合集成（7 个模型概率平均） | 0.9964 | — | 仅与单分支持平 |
| 逻辑回归 / 随机森林 / 极端随机树 | 0.9739 / 0.8767 / 0.8343 | — | 传统基线明显更低 |

> **如实说明**：双分支混合模型与单独 BiLSTM 分支的差异小于随机种子波动，
> 即**时序分支是主要贡献者**；概率集成同样只是持平。
> 初期我们曾用"卷积分支的差距随窗口变长单调收敛，说明它需要更长上下文"来解释这条负面结论，
> **但这个解释在后来的困难基准复测中被证伪**（见下文（4））：不是"还在收敛"，而是**始终没有增益**。
> 这条自我否定的过程完整保留在 `results/window_ablation.md` 与 `results/hard_ablation.md` 中。

**（3）窗口长度消融：本作品最重要的超参数（新增实验）**

窗口长度 T 是最重要的超参数，同时决定精度、误报率与检测时延。我们把消融做到 **T=48**，并对 T=16/24/32 **补足 3 个随机种子**（同一份数据、同一步长 stride=5、25 epoch）：

| T | 种子数 | 混合宏 F1 | 仅 CNN | 仅 BiLSTM | **混合 − 最好单分支** | 误报/小时 | 平均时延 |
|---|---|---|---|---|---|---|---|
| 10 | 1 | 0.9772 | 0.9415 | 0.9886 | −0.0114 | 28.31 | 6.6 ms |
| 16 | **3** | 0.9938 ± 0.0012 | 0.9727 ± 0.0059 | 0.9968 ± 0.0008 | **−0.0030** | 3.29 ± 5.14 | 17.1 ms |
| 24 | **3** | 0.9974 ± 0.0011 | 0.9791 ± 0.0020 | 0.9989 ± 0.0011 | **−0.0015** | 1.10 ± 1.90 | 24.3 ms |
| 32 | **3** | 0.9979 ± 0.0024 | 0.9840 ± 0.0018 | 0.9987 ± 0.0010 | **−0.0008** | **0.11 ± 0.19** | **35.4 ms** |
| 48 | 1 | 1.0000（饱和） | 0.9912 | 1.0000（饱和） | +0.0000 | 0.00 | 42.1 ms |

**结论一（负面结论，但这次是被"测穿"的）：卷积分支在流统计量特征上没有增益。** Δ 在每一个有置信区间的
窗口长度上都是负的（−0.0030 / −0.0015 / −0.0008），只是随 T 变长而收敛到 0，**从未转正**；到 T=48 双方都打满
1.0000（指标天花板），Δ 归零已无意义。因此早期"卷积需要更长上下文"的解释**被证伪**——它不是"还在收敛"，
而是**始终停在噪声内**（判据：Δ 全部不超过 1σ）。

> **我们自己抓到的假阳性（如实记录）**：T=32 最初只跑 1 个种子时 Δ 显示 **+0.0023**，看上去像"终于转正"；
> 补齐 3 个种子后 Δ 变成 **−0.0008**（落在 σ=0.0024 之内）——那个正值完全来自 seed 0 恰是三个种子里最好的那次。
> 这是"单种子 + 边缘显著不能当结论"的实证，也是本工程坚持每配置 3 种子的原因。

**结论二（正面结论，可直接用于部署）：加长窗口是压误报最省事的旋钮，而且让误报变得"可预测"。**
逐种子误报/小时：T=16 为 9.22 / 0.66 / 0.00（**波动 14 倍**）；T=32 为 0.00 / 0.33 / 0.00（**几乎为零**）。
**误报率不但下降（28.31 → 0.11 次/小时），种子间波动也从 14 倍收敛到几乎为零**——这对运维比"更低"更重要：
**误报率本身飘 14 倍的系统是没法标定工作点的。**

> **部署建议**：若业务能接受约 35 ms 时延，**T=32 用约 26 ms 的额外时延换掉约 84 倍的误报**（不动阈值、不动模型、
> 不重训，只改输入形状）；若时延预算只有十几毫秒，留在 T=16，改用阈值标定与连续确认压误报。
> ⚠️ T≥32 精度已饱和，那里的"精度对比"衡量的是**指标天花板**而非模型能力。
> **因此我们另造了一套困难基准把难度拉满后复测**，见下文（4）——结论是卷积依然没有翻身，
> "卷积需要更长上下文"的趋势本身也不成立。
> **交叉验证**：本表 T=16 的三种子（0.9938 ± 0.0012）与主实验（0.9940 ± 0.0011，不同轮数协议）互相印证。

**（4）困难基准复测：把难度拉满之后，卷积终于翻身了吗（本作品新增）**

（3）的结论有一个天然反驳：**T≥32 双方都打满 1.0000，是数据太简单，不是卷积没用。** 这个反驳很合理，
所以我们**另造一套困难基准**（数据目录 `data/raw_hard`、产物 tag `hard*`，与主实验完全隔离），
把与"可分性"直接相关的旋钮全部拉满，再用**完全相同的流程**重测一遍：

| 旋钮 | 简单基准（主实验） | 困难基准 | 作用 |
|---|---|---|---|
| `overlap_ratio`（与最易混淆类混合比例） | 0.35 | **0.70** | 直接改变类别边界 |
| `stealth_ratio`（隐蔽型攻击片段占比） | 0.45 | **0.80** | 攻击必须在窗口聚合层才看得出 |
| `stealth_mix`（隐蔽片段内伪装成正常样貌的流比例） | 0.45 | **0.70** | 压低单流层面可分性 |
| `feature_noise`（特征抖动） | 0.05 | **0.15** | 3 倍测量噪声 |
| `label_noise`（行级标注噪声） | 0.01 | 0.02 | 见下方诚实声明 |

**先证明"难度确实上去了"（用与架构无关的探针，避免自说自话）**：把 `(T,F)` 展平后跑逻辑回归，
窗口级宏 F1 从简单基准的 **0.9807 降到 0.8658**（降幅 0.115）；且**没有任何结构再打满**——
困难基准最高宏 F1 = **0.9891 < 1.0000**。**饱和问题被解决，这个基准能真正区分架构差异。**

| T | 简单 混合 | 简单 Δ | 困难 混合 | 困难 仅 CNN | 困难 仅 BiLSTM | **困难 Δ** | Δ 相对变化 |
|---|---|---|---|---|---|---|---|
| 10 | 0.9772 | −0.0114 | 0.8869 | 0.7918 | **0.8951** | −0.0082（−1.83σ） | +0.0032 |
| 16 | 0.9938 ± 0.0012 | −0.0030 | 0.9401 ± 0.0045 | 0.8263 ± 0.0497 | **0.9463 ± 0.0049** | −0.0061（−1.26σ） | −0.0031 |
| 24 | 0.9974 ± 0.0011 | −0.0015 | 0.9819 | 0.8351 | **0.9851** | −0.0032（−0.72σ） | −0.0018 |
| 32 | 0.9979 ± 0.0024 | −0.0008 | 0.9794 ± 0.0014 | 0.8484 ± 0.0203 | **0.9891 ± 0.0049** | −0.0097（−1.99σ） | −0.0089 |

① **卷积在困难基准上依然没有增益。** Δ 在**每一个 T 上都 ≤ 0**，最大值 −0.0032（T=24）；
最好单分支**每一个 T 都是「仅 BiLSTM」**。更贴题的一层证据是**逐种子配对**：同一种子下"混合 − 最好单分支"
共 **6 对，6/6 为负**（平均 −0.0079，符号检验双侧 **p = 0.031**）——**没有任何一个种子下混合模型更好**。
结论：T≥32 的饱和**不是**卷积翻不了身的原因。

② **趋势方向改变，"卷积需要更长上下文"被推翻。** 简单基准上 Δ 随 T **上升**（最小二乘斜率 +0.00043/条窗口，
从 −0.0114 收敛到 −0.0008）；困难基准上斜率变成 **−0.00003**，**T 最长档的 Δ 反而最负**（−0.0097）。
原假设预测"T 越长 Δ 越大"，实测方向相反。

③ **可解释的原因（不是只报一个负数）。**

| 基准 / T | 结构 | 末轮训练准确率 | 最优验证准确率 | 泛化差（训练−验证） | 测试宏 F1 |
|---|---|---|---|---|---|
| 困难 T=32 | 混合 | 0.9992 | 0.9932 | +0.0060 | 0.9794 |
| 困难 T=32 | 仅 CNN | 0.9917 | 0.8925 | **+0.0992** | **0.8484** |
| 困难 T=32 | 仅 BiLSTM | 0.9970 | 0.9940 | +0.0029 | **0.9891** |

- **卷积单支是困难基准上最脆弱的结构**：T=32 仅 CNN 宏 F1 0.8484，比简单基准同档 0.9840 低 **0.1356**（T=16 低 0.1464）。
- **混合模型是"过拟合式增益"**：T=32 混合模型训练准确率 0.9992（高于仅 BiLSTM 的 0.9970）、泛化差 +0.0060，
  但测试宏 F1 更低（0.9794 vs 0.9891）；参数量 151,434 vs 95,882。多出的卷积分支把训练集拟合得更满，测试集更差。
- **机理**：流统计量输入把"每条流的聚合量"当时间步，卷积要找的"相邻时间步局部组合模式"在特征工程阶段已被压平；
  难度一上来，它能抓到的局部模式**大多是噪声**，负贡献被放大。这与"卷积应当用在原始包序列/字节输入上"的既有判断一致——
  **本次设定（越难越依赖局部组合模式）恰恰是对卷积最有利的那一种，它依然没有翻身。**

④ **难度代价表**（同一结构 `cnn_bilstm`、同一 T=16，只换数据）：

| 指标 | 简单基准 | 困难基准 | 变化 |
|---|---|---|---|
| 多分类宏 F1 | 0.9938 | 0.9401 | −0.0536（−5.4%） |
| 误分类窗口数 | 14.7 | 124.0 | +109.3 |
| 在线误报（次/小时） | 3.29 | 14.88 | +11.59 |
| 平均检测时延 | 17.08 ms | 22.97 ms | +5.88 ms |
| **攻击片段召回** | 1.0000 | **1.0000** | **0** |

> **④的最后一行是本节最重要的实用结论**：难度翻倍后**分类精度掉 5.4 个百分点、误报涨 4.5 倍，
> 但"有没有攻击"仍然 100% 没漏**。精度指标在退化，**安全底线没有退化**——
> 这正是本作品把"攻击片段召回"而非"宏 F1"列为首要指标的原因。

> **诚实声明（我们调整过参数，全过程留档）**：困难档 `label_noise` 从建议的 0.05 下调为 **0.02**。
> 依据是**正式训练开始之前**的冒烟诊断：窗口级评估用 `pure_only` 过滤（窗口内有一条记录标签不一致即整条丢弃），
> 保留率 ≈ (1−label_noise)^T；0.05 时 **T=32 只剩 18.6% 候选窗口、最小类测试 support 仅 7 条**，
> 由此产生的宏 F1 颗粒度噪声（≈0.018）**大于待检验的 Δ 量级（0.001~0.01）**，该档将无法回答问题。
> 调到 0.02 后 T=32 仍有 2151 条测试窗口、最小类 support 30。**调整发生在 24 次训练全部开始之前，
> 没有任何模型结果作为依据**，且难度未被放松（线性探针 0.9807 → 0.8658）。
> 调整前后依据与全部数字见 `results/hard_ablation.md` 第 6 节，供评审自行判断。

> **口径提醒（防止误读）**：两套基准**数据内容不同**、测试窗口数也不同，因此"困难宏 F1 低于简单宏 F1"
> 只说明**难度上去了**，**不能**把两边绝对精度放在一起排名；本节检验的是**架构之间的相对关系 Δ**。
> 复现：`python tools/hard_ablation.py`（幂等，出表出图）；困难档训练命令见该报告第 8 节，
> 全程 `--set publish_summary=false`，主实验产物 SHA256 与 mtime 零变化（已逐一核对）。

**（5）分布漂移鲁棒性（`drift_strength=0.35`）**

| 模型 | 宏 F1（同分布） | 宏 F1（漂移集） | 退化 |
|---|---|---|---|
| CNN+BiLSTM（主模型，3 种子） | 0.9930 / 0.9956 / 0.9934 | 0.9934 / 0.9940 / 0.9918 | **−0.16% ~ +0.04%（基本不变）** |
| 仅 BiLSTM | 0.9964 | 0.9956 | −0.08% |
| 仅 CNN | 0.9670 | 0.9696 | +0.26% |
| 逻辑回归 | 0.9739 | 0.9739 | 0.00% |
| 随机森林 | 0.8767 | 0.7996 | **−7.7%** |
| 极端随机树 | 0.8343 | 0.7961 | **−3.8%** |

**在 T=16 的窗口下，时序深度模型对分布漂移几乎免疫（退化 ≤0.2%）**，而树模型仍退化 3.8%~7.7%。
窗口消融（见上一小节）解释了原因：更长的上下文让模型学到的是**多步演化模式**而不是单步阈值，
因此对"包规模/时长整体缩放"这类分布变化不敏感。这是"窗口化时序建模"最实用的价值。

**（6）错误分析：模型到底错在哪里（本作品新增，对应评审的"错误分析"验证方法）**

对 3,513 个测试窗口逐条分析（`tools/error_analysis.py`，结果见 `results/error_analysis.md`）：

| 项目 | 结果 |
|---|---|
| 总错误数 / 错误率 | 17 / **0.48%** |
| **漏报（攻击被判为正常）** | **0** —— 八个类别中 7 类的错误率为 0，唯一错误来自 Normal |
| 误报（正常被判为攻击） | 17（Normal 类错误率 0.680%） |

天然重叠，属于数据本身的模糊地带。后续可通过针对该类正常流量补样本、
或在工作点上选择更保守的阈值来进一步压低（见下一小节的工作点表）。

**（8）检测工作点选择：误报可控是本作品的核心设计（本作品新增）**

工业界的核心痛点（见 2.1）是误报，因此我们把「窗口长度 × 判定阈值 × 告警确认次数」
三个旋钮放在同一评估框架里全枚举（`tools/operating_point.py`，**无需重训即可得到全部工作点**）：

| 阈值 | 确认窗口数 | 攻击片段召回 | 误报次数 | 误报/小时 | 平均检测时延 |
|---|---|---|---|---|---|
| 0.30 | 1 | 100% | 34 | 11.19 | 9.9 ms |
| **0.50（原默认）** | **1** | **100%** | **26** | **8.56** | **9.9 ms** |
| 0.50 | 2 | 100% | 4 | 1.32 | 14.3 ms |
| **0.50（现默认）** | **3** | **100%** | **2** | **0.66** | **18.1 ms** |
| 0.50 | 5 | 100% | 0 | **0.00** | 32.3 ms |
| 0.90 | 3 | 100% | 0 | **0.00** | 19.5 ms |

**结论**：在**保持攻击片段召回 100%** 的前提下，仅通过"连续确认 3 个窗口"就把误报
从 8.56 降到 **0.66 次/小时（降低 92%）**，代价是平均时延增加 8 ms；
若要求零误报，可用"阈值 0.90 + 确认 3"（19.5 ms）。
**运维可以按自己的误报预算直接换点**，这正是对 SANS 调查所指"误报是第一痛点"的直接回应。

切分、清洗与预处理口径与主实验完全一致。）

| 切分口径 | 测试集规模 | 多分类准确率 | 二分类 F1 | 二分类 ROC-AUC | 误报（次/小时） |
|---|---|---|---|---|---|
| ① 分层随机切分（按行） | 45,662 | 0.9998 | 0.9998 | 1.0000 | — |
| ② **按会话分组切分**（Flow ID，84,252 组） | 46,190 | **1.0000** | 1.0000 | 1.0000 | 0.00 |

**（10）关于真实数据集高分的原因诊断（重要，如实披露）**

我们对"近乎满分"的结果做了两项独立诊断：

| 诊断项 | 结果 | 含义 |
|---|---|---|
| 测试样本到训练集最近邻距离（标准化空间）中位数 | 0.0004 | 绝大多数测试流在训练集里有"几乎一样"的邻居 |
| 距离 < 0.01（几乎完全相同）的测试样本占比 | **84.95%** | 数据集存在**大量近似重复** |
| 1-最近邻分类器（纯记忆式基线）准确率 | **0.9985** | 仅靠"找最像的一条"就能接近满分 |
| 本作品模型准确率 | 0.9998 | 与 1-NN 差距很小 → 该数据集上的高分主要来自数据冗余 |
| 单特征 + 单阈值（决策树桩） | 0.8051（最好单特征 0.8583） | 单特征不足；但 65 维联合空间高度可分 |
| 去近似重复 + 按组切分（最严口径） | 0.9976 / AUC 0.9996 | **即使消除冗余，该数据集仍高度可分** |

**结论（两点，都如实写入报告）**：
1. 该公开数据集**既冗余又确实高度可分**——它适合用来验证"流水线在真实数据上能否端到端跑通"，
   但**不能用来区分模型优劣，也不代表真实泛化能力**；
2. 因此我们把**自研的高难度仿真数据集作为主要评估基准**：在该数据集上随机森林仅 0.878、
   主模型 0.985，存在真实且可复现的差距，并配有消融、漂移与多种子统计。
   这恰好说明：**公开数据集的"高分"往往是数据本身造成的，而不是方法更强**。

**（11）运维工作量换算：把算法指标翻译成值班室听得懂的话（本作品新增）**

在线告警级指标（次/小时）仍然不是运维语言。我们用 `tools/ops_impact.py` 把它换算成
**告警量/天、人工处置工时/天、漏报次数/天、容量预警线**（结果见 `results/ops_impact.md`）：

换算口径（三点，均明确标注，避免"实验室数字冒充生产数字"）：
① **误报率**取 3.04 小时在线回放的实测值外推到天（该量与攻击密度无关，可以外推）；
② **真实告警量**取决于目标环境每天真正发生多少次攻击，按业务假设 **20 次/天**折算
（测试流是刻意做成攻击密集的，直接外推会把告警量虚高十几倍——这是常见的方法学错误，我们明确规避）；
③ 单条告警按 **6 分钟**排查、一个班次按 **8 小时**折算（可调参数）。

| 工作点 | 误报/小时 | 误报/天 | 告警/天 | 误报占比 | 人工工时/天 | 平均时延 | 漏报/天 |
|---|---|---|---|---|---|---|---|
| 阈值 0.50 + 确认 **1**（不做确认） | 8.56 | 205.4 | 225.4 | 91.1% | **22.5 h（≈2.8 个班次）** | 9.9 ms | 0 |
| 阈值 0.50 + 确认 **3**（工程默认） | 0.66 | 15.8 | 35.8 | 44.1% | **3.58 h** | 18.1 ms | 0 |
| 阈值 0.90 + 确认 **2**（误报预算内最优） | 0.33 | 7.9 | 27.9 | 28.3% | **2.79 h** | 16.1 ms | 0 |
| 阈值 0.90 + 确认 **3**（零误报点） | 0.00 | 0.0 | 20.0 | 0.0% | **2.00 h** | 19.5 ms | 0 |

**结论**：
1. **不做「连续确认」的系统在 1× 流量下就已经超出值班人力**（22.5 人工小时/天 ≈ 2.8 个班次），
   即"误报本身会变成事故"；加入确认后降到 3.58 小时/天（占一个班次的 45%），
   而**攻击片段召回没有任何下降**（均保持 100%）——这个几乎零成本的机制每天省下 **19 个人工小时**；
2. **响应量级差**：攻击出现到报警平均 **18 毫秒**（P95 71 毫秒），对比人工巡检的分钟—小时级；
3. **诚实的容量边界**：误报随决策窗口数线性增长，流量放大 10× 时人工占用由 45% 升至 222%，
   因此**规模每上一个量级都必须重新标定工作点**。我们不声称"无限流量下都够用"，
   这张表本身就是给容量规划用的预警线。

**（12）控制器原生字段口径：字段不够时，代价有多大（本作品新增）**

上线前最尖锐的问题是："模型用了 84 列 CICFlowMeter 特征，**真实 SDN 控制器取不到这些字段怎么办**"。
我们把这条路也走通了：仅用 **OpenFlow 流表统计可提供的 17 列**（`packet_count`、`byte_count`、
`flow_duration_sec/nsec`、`tp_src/tp_dst`、`ip_proto`、`flags` 及各派生速率，与本仓库 Ryu 采集脚本同款字段），
重新生成数据、重新训练（8 类）、重新评估：

| 特征口径 | 特征数 | 宏 F1 | 二分类 F1 | ROC-AUC | TPR@1%FPR | 片段召回 | 推荐工作点 | 平均时延 |
|---|---|---|---|---|---|---|---|---|
| 完整流特征（inSDN/CICFlowMeter 风格） | 71 | **0.9940** | 0.9918 | 0.9999 | 1.0000 | 100% | 阈值 0.50 + 确认 3 | 18.4 ms |
| **控制器原生字段（OpenFlow 流表统计）** | 17 | 0.8441 | 0.8533 | 0.9951 | 0.9151 | **100%** | 阈值 **0.99** + 确认 5 | 40.6 ms |

**结论**：只用控制器原生字段时，**攻击片段召回仍为 100%**（该发现的一个都没漏），
但**工作点必须大幅收紧**（阈值 0.50→0.99、确认 3→5），代价是**检测时延由 18 ms 升至 41 ms**，
窗口级宏 F1 由 0.994 降到 0.844。也就是说：**字段缺口转化为"工作点代价"，而不是"功能失效"**。
这条量化边界直接决定了两件事：① 没有独立探针的纯 SDN 环境里这套系统能用到什么程度；
② 该优先补哪几类字段（完整口径多出的正是**双向包间隔与标志位统计**）。
两个口径封装在同一个服务里，一条参数即可切换且**服务与大屏同步口径**。

**（14）跨域适用边界：我们主动做的一次"失败实验"（本作品新增）**

最苛刻的设定是**零样本跨域**：把自研数据集上训练好的模型直接拿去推理真实 inSDN，
不在真实数据上训练、不微调、不重拟合任何参数（71 维特征按语义 100% 映射成功）。
结果与逐级校准如下（完整报告含 71 维逐特征漂移明细：`results/cross_dataset_report.md` / `.json`）：

| 设定 | 需要标注 | ROC-AUC | 二分类 F1 | 1% 误报预算下的召回 |
|---|---|---|---|---|
| 同域（有目标域数据，按正常流程训练） | 全部 | 0.9996 | 0.9986 | —（准确率 0.9976） |
| 零样本跨域（自研 → 真实，直接推理） | 0 | 0.6697 | 0.5629 | 0.0006 |
| 只重新拟合标准化器（无需标签） | 0 | **0.4742** | — | 0.0002 |
| +500 个标注窗口微调分类头（3.1 s） | 500 | 0.7034 | 0.5965 | **0.4257** |
| +解冻主干再训 2 epoch（共 6.6 s） | 500 | 0.7657 | 0.6150 | **0.4453** |

**三条结论（都如实写进报告）**：

1. **零样本跨域不可用**（二分类 F1 0.5629、误报率 21%），而且**只重新拟合标准化器会把 AUC 从 0.6697
   打到 0.4742**——零样本那点排序能力有相当一部分来自"漂移幅度本身"造成的假信号
   （攻击行偏离合成分布更远，被误打误撞排到前面），把量纲拉回目标域口径就消失了。
   这条反直觉结论的实用价值是：**跨域 AUC 高不能被当作"模型还能用"的证据**。
2. **真正有效的是少量目标域标注**：500 个窗口、3 秒微调分类头，召回由 0.0006 提到 0.4257；
   再解冻主干 6.6 秒提到 0.4453，但仍远低于同域的 0.9986。逐特征漂移诊断指出根因是
   **采集口径差异**（CICFlowMeter 的流切分/超时/子流定义），而非模型结构：
   重定标后"正常流量像不像训练数据"确实修好了（评估段 |z-shift| 均值 0.4956→0.2089、
   超 1σ 特征 7/71→1/71），但"攻击长什么样"修不了（攻击行仍 |z| 均值 0.275、最大 2.94）。
3. **正确的下一步不是继续调模型，而是用目标域统计量反向标定生成器参数（域随机化）**——
   本作品生成器的均值/方差/重尾参数都是显式可调的，这正是把它做成参数化工具的价值所在。
   另需说明：该公开数据的窗口并非真实时序（按攻击类型分块拼接发布），
   故上表数值应视为"**窗口级分类**"的上界参考，**不等于在线检测召回率**。

> 说明这件事的意义：**一个能上线的东西必须知道自己在什么条件下会失效、以及把失效补回来要付多少代价**。
> 同时请注意对照——同一个模型与流水线，在**有目标域数据**时（同域训练/评估）在该真实数据集上
> 可达 0.9976–1.0000（见 5.3(8)），所以失效的原因是域漂移与采集口径，而不是模型或工程本身。

**（15）未知攻击（开集）检测：训练时没见过的新型攻击会怎样（本作品新增）**

前面所有指标都建立在"8 类已知攻击"上。但真实网络里最要命的问题是：**出现训练时从未见过的新型攻击时，
系统会不会把它硬塞进某个已知类别、还给出很高的置信度？** 我们做了开集实验——**把整类攻击从训练/验证中
拿掉**（留出 U2R、留出 Botnet 两个场景 × 3 个种子），测试集里保留该类作为"未知攻击"，
OOD 阈值只在**已知类的验证集正常窗口**上标定（测试集与留出类绝不参与标定）：

| 留出场景 | 不做任何拒识时会怎样（最危险的一组数据） | 未知检出率 UDR @1% / @0.1% 误报预算 | 已知类宏 F1 代价 |
|---|---|---|---|
| **留出 U2R** | 42 个未知窗口 **100%** 被安上已知标签：**84% 判成 WebAttack**、13% DoS；平均最大概率 0.82、**42% 的错判置信度 ≥0.9** | **69.8% / 30.2%**（energy 分数） | 0.9931 → 0.9881（−0.5 pt） |
| **留出 Botnet** | 73 个未知窗口 **100%** 被安上已知标签：**96% 判成 Normal** —— 攻击**连告警都不触发**，比错报成另一种攻击更危险；74% 置信度 ≥0.9 | **44.3% / 0.9%**（energy 分数） | 0.9931 → 0.9942（**无代价**） |

**三条结论（都写进报告）**：

1. **不做拒识的后果是"自信地把新攻击叫成老朋友"**：未知窗口 100% 被安上某个已知类标签，
   U2R 场景 42%、Botnet 场景 74% 的错判置信度 ≥0.9。运维会按**错误的攻击类型**去处置，
   这比漏报更容易造成误判性事故。
2. **拒识有效，但强烈依赖"未知攻击与已知/正常流量有多像"**：机理独特的 U2R 在 1% 误报预算下能捞出
   **69.8%**；而与正常流量形态接近的 Botnet（C2 心跳、低速率、长连接）**1% 预算下只有 44.3%，
   0.1% 预算下几乎失效（0.9%）**。**AUROC 会骗人**——三种 OOD 分数（`1−max softmax` / 熵 /
   能量分数）的跨场景 AUROC 都在 0.978 左右，但**低误报预算下的尾部表现差一个数量级**。
   这条"AUROC 好 ≠ 尾部可用"的结论，对任何做异常检测的人都适用。
3. **拒识几乎不伤已知类**：加拒识后已知类宏 F1 反而略升（0.9881→0.9928 / 0.9942→0.9946），
   因为被误拒的已知攻击仍然会告警（只是标签变成"未知"）。因此正确用法是**叠加而非替代**：
   二分类头负责"是不是攻击"，OOD 分数负责"是不是已知类型"，未知告警进人工研判队列，
   确认后把样本回流训练集，形成「未知 → 已知」的闭环。

> 部署建议（报告 8.1 节）：优先用能量分数 `-logsumexp(logits)`；阈值在生产环境的正常流量上取分位数
> （1% 预算取 99 分位）；**未知告警比例本身就是一条免费的漂移指标**，突然升高通常意味着新攻击出现或
> 流量分布变化。诚实边界：留出类样本量小（42 / 73 个窗口），且本实验的"未知"来自同一数据生成器，
> 与真实新型攻击仍有差距；与已知类机理接近的新攻击（例如只改端口/速率的 DoS 变种）仍会失效。

| 元素 | 内容 |
|---|---|
| 未知占比随时间的曲线 | 按真实判定窗口分箱，每格显示被标为「未知形态」的窗口占比，并画出标定阈值对应的参考线（1% 误报预算） |
| 攻击构成堆叠图 | 同一时间轴上各类别被判为攻击的窗口占比（攻击构成的迁移一眼可见） |
| 回放游标 | 精确跟随播放位置（与窗口级缓存逐行对应） |
| 一键跳峰 | 「跳到未知占比最高处」——实测跳到第 4260 行（该格未知占比 **6.78%**、全局 0.80%） |
| 降级提示 | 找不到标定文件时明确显示「未标定，面板不可用」，**不伪造参考线** |

**两条必须写清的边界**：① 熵高只代表模型低置信 / 分布平坦，**不等于"检测到未知攻击"**（面板文案刻意用
「未知形态」而非「未知攻击」）；② 在本数据集上**攻击窗口的熵均值（0.005）反而低于正常窗口（0.023）**，
因此"峰格与某类攻击重合"有巧合成分——真正的未知攻击识别能力边界以 (13)/(14) 的留出实验为准。

**（20）真实抓包接入：pcap → 控制器原生 17 字段（`tools/pcap_to_flows.py`，本作品新增）**

仿真数据的可信度永远会被质疑。此前项目有两条数据接入路径（完整流特征 / 控制器原生字段），
本作品补上第三条：**拿到一段真实抓包文件，直接算出流特征并检测**（离线取证、事后复盘场景，
不需要控制器在场）。

| 项目 | 支持情况 |
|---|---|
| 格式 | 经典 `.pcap`（微秒 `0xa1b2c3d4` 与纳秒 `0xa1b23c4d`，**大小端 4 种组合均有测试**）、`.pcapng`（SHB/IDB/EPB，含 `if_tsresol` 与二进制 2^-n 时基） |
| 链路层 | Ethernet(1)、RAW IP(101)、IPV4(228)、LINUX_SLL(113)、LINUX_SLL2(276)——覆盖 `tcpdump -i any` 的 cooked 抓包；802.1Q 与 QinQ 可多层剥标签 |
| IPv4 分片 | 正确解析 IHL 与分片标志；**首片计入本流，非首片跳过并计数**（非首片没有传输层头，与控制器统计口径一致） |
| 切分 | 空闲超时（`--idle-timeout`，默认 15 s）与硬超时（`--hard-timeout`，默认 120 s），与 OpenFlow 流表项的 idle/hard timeout 等价 |
| 依赖 | **纯标准库，不需要 scapy，未引入任何新依赖** |
| **往返一致性** | 自造 800 条流的抓包 → 解析回 **800/800 条流**（1:1，无多余合并/拆分）；**17 个特征 × 800 条流全部逐位一致**；`packet_count` 完全一致 800/800；UDP/TCP 端口 682/682；时长最大偏差 **12.9 µs**（容差 29 µs）；Σ`packet_count`=3207=解析报文数（守恒） |
| 能量自检 | 解析后自动校验 `packets/s ≈ packets/时长`、`bytes ≥ packets×20` 等，违例打印告警（不静默） |
| 行为测试 | `tests/test_pcap_tools.py` **58 项**：往返一致性、空/截断/非法文件、大小端、VLAN、pcapng 时基、超时切分、`--max-flows`，以及**自检器有效性**（能抓出人为破坏的速率列，不是永远说 OK） |

**一条命令即可闭环**：`tcpdump -i eth0 -s 0 -w capture.pcap` →
`python tools/pcap_to_flows.py --input capture.pcap --output flows.csv` → 检测。
**诚实局限**：这条路径只算控制器口径的 17 个字段，与 CICFlowMeter 的完整口径（含子流/Bulk/IAT
统计量）不同，因此**精度上限就是控制器原生口径的水平（宏 F1 0.8441）**；要更高精度仍需完整流特征。

**尚未达到的目标（如实说明）**：
① CNN 分支未体现出增益，需要更长窗口或原始包序列输入才能验证其价值；
② 未做对抗样本鲁棒性测试；
③ 未在真实生产网络长期运行，误报率（0.55 次/小时，工作点可调）在真实环境中的表现仍需现场标定；
④ Ryu 适配层已在真实 ryu-manager + 真实 OF1.3 线协议下跑通（16/16），但**物理交换机与真实攻击流量仍未覆盖**；
⑤ 控制器原生字段口径的精度（宏 F1 0.844）尚不足以替代完整流特征口径，需补齐双向包间隔等字段；
⑥ 零样本跨域迁移不可用，即便用 500 个目标域标注微调后召回也仅 0.4453（1% 误报预算），
   需靠生成器侧域随机化才能根本解决；
⑦ 跨域实验依赖未标注许可证的真实数据集（依规不再分发），公开仓库中默认不可一键复现，
   全部数值已固化在 `results/cross_dataset_report.md`。

**（21）P0+P1 六项补充实验（本轮新增，对应"把已知短板逐条补上"）**

前面（1）~（20）解决了"能不能跑、准不准、能不能上线"；这一组六项实验解决的是**把已知短板逐条补上**，
每一项都有独立工具、可复现产物与事前写死的判据。结论一并给出（含**两条负面结论**）：

① **包序列输入复研**（`tools/packet_seq.py`，`results/packet_seq.md`）
把输入从"流级聚合量的时间窗"换成"流内有序包序列"（同一批 24,000 条流，同数据对照）：

| 表示 | 仅 CNN | 仅 BiLSTM | 混合 | GAP（CNN 落后） | Δ（混合−最好单分支） |
|---|---|---|---|---|---|
| 流级滑窗 T=16 | 0.8325 | 0.9679 | 0.9337 | **0.1354** | −0.0342 |
| 包级 前 32 包 | 0.3535 | 0.3606 | **0.3760** | **0.0071** | **+0.0155** |
| 包级 前 64 包 | 0.3066 | 0.3623 | **0.3905** | 0.0557 | **+0.0282** |

卷积的落后程度缩小 19 倍；且包级 T=32/64 出现**逐种子配对 3/3 为正**的正增益（全项目首次）。
总判定 **mixed**（换成全量主实验参照时只有 T=32 通过）——两个参照都报。**诚实标注**：
包级绝对宏 F1 仅 0.31~0.39，这是机理探测，不等于"包级更好用"。

② **对抗鲁棒性实测**（`tools/adversarial_eval.py`，`results/adversarial_eval.md`）
白盒、特征空间、L∞ 有界，扰动投影回训练集逐特征取值范围（物理可行），并与同范数随机扰动对照：
ε=0.10/0.20/0.30/0.50 时 PGD 把宏 F1 从 **0.9930** 压到 0.8711/0.6083/0.4802/0.3731，
**逃逸率 22%/57%/73%/84%**；随机扰动几乎无影响（≥0.9887）→ 退化来自定向优化。
在线口径：无攻击 24/24 片段召回 → ε=0.2 时 14/24、ε=0.5 时 **8/24**。
对抗训练（clean+FGSM 各半）干净代价 **−0.0069**、ε=0.2 收益 **+0.1237** → 按事前判据**划算**。
**负面发现**：对抗样本的预测熵没有升高（0.0177 → 0.013~0.032，未知阈值 0.3914）→
已有的「熵超阈值」机制**拦不住**对抗样本。

③ **现场标定**（`tools/calibrate_online.py`，`results/calibration.md`）
按误报预算反解「阈值 × 确认次数」并支持**热写回**服务。三种标定段的整条流验证：

| 标定段 | 反解 | 召回 / 时延 / 误报 |
|---|---|---|
| 安静时段（43 段 0.83 h） | 0.995 + 确认 1 | **100% / 15.8 ms / 0.00 次·h⁻¹** |
| 工程默认（不调参） | 0.50 + 确认 3 | 100% / 18.1 ms / 0.66 次·h⁻¹ |
| **反例：含攻击的开头段**（1,777 攻击行） | 1.000 + 确认 1 | **4% / 2.95 s / 0.00 次·h⁻¹** |

反例是本节最重要的产出：**拿含攻击的时段标定，召回从 100% 掉到 4%**。工具同时给出
**样本充足性判据**（预算 B 次/小时至少需要 3÷B 小时安静流量），本次 0.83 h < 3 h →
报告显著标注"预算估计不可靠、以默认工作点为准"。

④ **长稳回放**（`tools/soak_test.py`，`results/soak_test.md`）
进程内服务连续回放 **9.1 小时等价流量**（3 轮 × 3.04 h、36 桶、不限速），三项事前判据全过：
内存 **+13.6 MB**（门槛 ±64）、时延比 **1.01**（门槛 ≤1.5）、告警漂移比 **1.14**（门槛 ∈[0.5,2]）。
这把"未在真实生产网络长期运行"缩小为"本机连续回放 9 小时等价流量无退化"（**不能**替代生产验证）。

⑤ **域随机化跨域**（`tools/domain_randomization.py`，`results/domain_randomization.md`）——**负面结论**
造 6 个域（基准/隐蔽攻击/边界模糊/强噪声/老式攻击/业务构成变化），逐个留一域零样本，并加**等预算对照**：
平均增益仅 **+0.0063**（3 正 3 负，符号检验 p=1.0）→ 判定 `not_supported`。
结构上：对"老式明显攻击" **+0.22**、"类别边界模糊" **+0.10**，但对"隐蔽攻击为主" **−0.25**；
等预算对照（同样本量、更多多样性）在 **5/6 折上比单域更差** →
在这个难度范围内 **"每域数据量"比"域的数量"更重要**。
方法论坑（已写入报告）：用"复制同一域"对齐数据量会因管线去重而**逐位相同**，等预算只能靠多域抽样。

⑥ **控制器原生字段扩展**（`tools/controller_fields.py`，`results/ctrl_field_extension.md`）
（5）与（12）已经量化过"字段缺口"：17 列口径宏 F1 **0.8441**、须阈值 0.99 + 确认 5、时延 41 ms。
本次把控制器**真能算出来**的字段补上：`avg_pkt_size`（一步除法）+ 轮询窗口内的流表聚合
（`src_distinct_dport`、`src_dport_entropy`、`src_short_flow_ratio`、`src_new_flow_rate`、
`dst_distinct_src`、`dst_src_entropy`、`src/dst_flow_count`、`table_flow_count`、`proto_share`），
17 列 → **30 列**，两个口径**同一批流、同结构、同窗口、3 种子**对比：

| 口径 | 特征数 | 宏 F1（3 种子） | 误报预算 1 次/h 的工作点 | 平均时延 |
|---|---|---|---|---|
| 控制器原生 17 列 | 17 | **0.8183 ± 0.0104** | 阈值 0.985 + 确认 5 | 39.8 ms |
| **+ 可推导聚合量（本次）** | **30** | **0.9956 ± 0.0004** | 阈值 **0.3** + 确认 **2** | **14.0 ms** |
| 完整流特征口径（参照） | 71 | 0.9940 | — | 18.4 ms |

Δ = **+0.1772**（σ=0.0104，≈17σ）：控制器原生口径**追平完整流特征口径**（差距 0.1757 → **−0.0016**），
且**工作点更宽松**（阈值 0.985→0.3、确认 5→2、时延 39.8→14.0 ms）。同时给出
**明确不可得字段清单**（TCP 标志位计数、IAT/包长分布、头部长度、活跃/空闲周期、subflow/bulk 统计）——
**扩展不可能靠"伪造报文级量"实现，因为 OpenFlow 流表统计本身不含这些量**。
两条必须一起看的诚实说明：① 聚合窗口已改为**因果的**（只看过去 60 秒）——最初版本用了 ±60 秒对称窗口（含未来行），
那是**前视泄漏**且与真机行为不符，上表是修正后的数字；② 聚合量天然携带"战役级"形态
（一个源打很多端口、很多源打同一目的），这在真实 SDN 里同样可算，但真实流量会更嘈杂。

⑦ **开集拒识改进**（`tools/openset_ood_plus.py`，`results/openset_ood_plus.md`）
在特征空间（融合层 256 维）上补 **马氏距离**与 **KNN 距离**两种分数（复用已训练开集模型，不重训）：

| 场景 | 基线最佳 UDR@1% | 马氏距离 UDR@1% | UDR@0.1% 基线 → 马氏 | 已知攻击误拒@1% |
|---|---|---|---|---|
| U2R | 0.6984（energy） | **1.0000** | 0.3016 → **0.8730** | 0.0045 → 0.0302 |
| Botnet | 0.4429（energy） | **1.0000** | 0.0091 → **0.9087** | 0.0053 → 0.0606 |

最严预算（0.1%）下 Botnet 从 **0.9% → 90.9%**；**自我怀疑诊断**（只看特征范数偏离）UDR 仅 0.4%~5%
→ 提升不是"范数偏移"这种平凡信号；KNN 分数**无效**（0.1984 / 0.3151），如实列出。
代价：已知攻击误拒从约 0.5% 升到 3.0%~6.1%，按事前判据（代价不得变差 >2 pt）判为 **`partial`**。

> 六项实验的隔离方式一致：**绝不重新生成 `data/raw` 主数据**；辅助实验一律独立目录 + `publish_summary=false`；
> 每项跑完核对主实验产物的 SHA256 与 mtime 零变化；判据**事前写死**，不事后调整。

1. **真实 Ryu 控制器进程**：用官方 `ryu-manager`（**Ryu 4.34，独立 venv**）加载本作品的
   `integrations/ryu_guard.py`（**不是桩件**），验证适配层能在真实运行时里 import、注册事件、被 app 加载器接管；
2. **真实 OpenFlow 1.3 线协议**：脚本实现一个**模拟交换机**，用真实 TCP + 真实 OF1.3 报文与 Ryu 完成
   完整握手、上报 `OFPFlowStatsReply`（正常轮 + 攻击轮，流量取自真实数据集测试流），
   再逐字段解析控制器回发的 `OFPFlowMod`，并与控制器侧审计台账（`executed=true`）对账。

**结果：16/16 项检查通过，Ryu 侧 0 条报文解析错误。** 关键证据：

| 检查 | 结果 |
|---|---|
| OF1.3 握手（HELLO / FEATURES / PORT_DESC） | ✅ 实收控制器报文序列 HELLO→FEATURES_REQUEST→PORT_DESC→FLOW_MOD→… |
| 控制器进入 MAIN_DISPATCHER 并识别交换机 | ✅ Ryu 日志出现适配层的「交换机上线」记录，datapath 已注册 |
| 周期性拉取流表统计（`OFPMP_FLOW`） | ✅ 收到 4 次请求，交换机回 2 条 `OFPFlowStatsReply` |
| 线格式合规 | ✅ Ryu 侧解析错误 **0** 条 |
| 攻击轮 → 告警 → 下发规则 | ✅ 交换机实收 1 条 `priority=100`、`ipv4_src` 精确匹配的 DROP 流表项 |
| 正常轮 → 无动作 | ✅ 针对正常源 IP 的规则 **0** 条（处置路径有选择性） |
| 台账与报文一致 | ✅ 10 条告警：1 条真实下发、9 条幂等抑制，台账 `executed=true` 与报文逐项对上 |

**这一轮的价值主要在「抓到了什么」——4 个真 bug 全是单元测试必然漏掉的**：

1. **multipart 子类型写错**（`OFPMP_FLOW` 写成 `0`，而 0 是 `OFPMP_DESC`）：Ryu 拿 1056 字节的
   desc 结构去解流表统计，直接抛 `struct.error` 丢弃整包——现象是**TCP 通、握手通、链路上毫无异常，
   但控制器永远不会告警**。自检里补了「常量表与规范逐条核对」这一项防回归。
2. **OF1.3 握手比规范文档多一步**：Ryu 收到 `FEATURES_REPLY` 后**不会**直接进 `MAIN_DISPATCHER`，
   还要先发 `OFPPortDescStatsRequest`、等交换机回 `OFPPortDescStatsReply` 才切状态
   （`ryu/controller/ofp_handler.py:216-232`）。少了这一步，适配层的 datapath 列表永远是空的，
   **周期性拉流表这件事根本不会发生**。
3. **OXM TLV 之间不该逐条补齐**：只有整个 `ofp_match` 才补齐到 8 字节。此前每条 TLV 各自补齐，
   「自己发自己收」完全自洽，只有真实 Ryu 按 `length` 连续推进会解析失败。现在自检里直接比对
   **Ryu 自己序列化出的黄金字节向量**，不再只做自洽性检查。
4. **处置幂等**：一次持续攻击会连报十几个滑动窗口，早期实现每报一次就下发一条规则，
   交换机上会多出十几条内容完全相同的流表项。已改为「同一源 IP 在封禁窗口内只下发一次」，
   台账区分「真实执行」与「幂等抑制」，并补了回归测试。

**仍然成立的边界**：物理交换机、真实攻击流量、厂商私有扩展未覆盖；三者都在报告里写明。
复现：`python tools/ryu_live_check.py --self-test`（秒级、免装 ryu）；
整套：`python tools/ryu_live_check.py --ryu-python <装了 ryu 的解释器>`。

## 八、总结与展望

### 8.1 项目总结

本作品把一份不可复现、评估口径有误的研究型 demo，重构为一个可复现、可演示、可复用的开源工程：
以滑动窗口 + CNN/BiLSTM 双分支 + 多任务双头为核心模型，配套自研流量生成器、三套评估口径、
12 类图表与离线演示大屏，并完成 **116 项交付自检**（含 10 项单元测试 + 28 项 Ryu 适配层行为测试）。
在自研难度可控数据集上取得宏平均 F1 **0.9940 ± 0.0011**、攻击片段召回 **100%**、
平均告警时延 **18.4 ms**、误报 **0.55 次/小时**（且给出 0~11 次/小时的完整工作点表供运维选择）；
在此之上通过**窗口长度消融**给出了可直接用于部署的结论（窗口加长可再把误报降低 88%），
并在真实公开数据集上验证了流水线的端到端可用性，**主动诊断并披露了该数据集 85% 的近似重复问题**。

团队收获：掌握了完整的"算法研究 → 工程化 → 可复现交付"链路，
以及**如何识别并避免数据泄漏、如何诊断公开数据集的隐藏陷阱**。

未完成事项：CNN 分支虽随窗口变长差距收敛，但仍未取得正向增益（需原始包序列输入进一步验证）；
对抗鲁棒性未测试；真实生产环境部署未验证。

### 8.2 后续计划

1. 功能优化：原始包序列 / 字节级输入（困难基准复测已排除"窗口不够长"这一解释，见实验（4）），继续验证卷积分支价值；
2. 测试扩展：增加对抗样本、跨数据集泛化测试；接入 CI 自动回归；
3. 开放维护：补充英文文档、示例数据与 issue 模板；
4. 应用推广：与 SDN 控制器对接，形成"采集—检测—告警"闭环演示。
