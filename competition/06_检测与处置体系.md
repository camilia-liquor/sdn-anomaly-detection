# 检测与处置体系

> 本文回答一个评委一定会问的问题：**已知攻击怎么处理？未知攻击怎么处理？漏报怎么办？处置错了怎么办？**
> 每一项都标注 **【已实现】**（有代码与产物，可复现）或 **【设计中】**（有明确规则但代码未落地），
> **不把设计写成已实现**。对应产物见文末清单。

## 0. 体系总览（七层闭环）

```
① 采集        控制器流表轮询 / pcap 解析 → 控制器原生字段口径（17 维）或完整流特征（71 维）
                          ↓  ★ 输入形状校验：不符则拒绝启动，绝不带错口径推理
② 判定        多任务双头模型（8 类 softmax + 攻击 sigmoid）
              三路分数：① 攻击概率 ② 多分类置信度 ③ 新颖性分数（开集拒绝）
                          ↓
③ 分级        四类状态：正常 / 低置信观察 / 已知攻击（带细类）/ 未知形态
                          ↓
④ 确认        连续 N 窗口确认 → 抑制抖动
              （CIC-IDS2017 真实数据实测：N=1→2→3，误报 254 → 56 → 13 次）
                          ↓
⑤ 处置        动作矩阵（阻断 / 限速 / 只告警 / 观察）＋ 幂等下发 ＋ 审计台账
                          ↓
⑥ 留痕        告警台账 ＋ 观察池（差一点到阈值的窗口）＋ 环形缓冲（回看"为什么没报"）【已实现】
                          ↓
⑦ 复盘回流    人工研判 → 标注回流训练集 → 定期重标定 → 门槛复检
```

## 1. 已知攻击的处理

### 1.1 判定能力【已实现】

| 项 | 实测 |
|---|---|
| 8 类多分类（Normal / DDoS / DoS / Probe / BruteForce / WebAttack / Botnet / U2R） | 合成域宏 F1 **0.9930~0.9956**（3 种子，均值 **0.9940**；s0 = 0.9930） |
| 控制器原生字段口径（17 列，不依赖 pcap 全特征） | 宏 F1 **0.8441**（种子 s1 达 **0.8816**）；特征扩到 30 列后 **0.9956 ± 0.0004** |
| 逐类在线表现 | 全部片段召回 100%；**逐类确认时延差异极大**：Probe 5.5 ms、DDoS 13.5 ms、BruteForce 43.6 ms、WebAttack 99.1 ms、U2R 164.2 ms、**Botnet 857 ms** |
| 处置闭环 | 真实 ryu-manager + 真实 OpenFlow 1.3 线协议 **19/19 项通过** |

### 1.2 动作矩阵【已实现】

处置动作**不是一刀切**，由「攻击类型 × 置信度 × 业务危害」决定：

| 攻击类型 | 典型机理 | 默认动作 | 依据 |
|---|---|---|---|
| DDoS | 洪泛，流量放大 | **阻断**（drop） | 确认快（13.5 ms）、危害直接 |
| DoS | 慢速/连接耗尽 | **阻断**；低速变种先**限速** | 时延 27.4 ms，低速型需观察 |
| Probe | 端口/资产扫描 | **阻断 + 记录源** | 5.5 ms 即可确认 |
| BruteForce | 口令爆破 | **限速 + 告警**（避免误封正常登录源） | 时延 43.6 ms |
| WebAttack | 注入/XSS | **告警 + 限速**（阻断易误伤业务） | 时延 99.1 ms |
| Botnet | C2 心跳，低速长连接 | **告警 + 长期观察**（不急阻断，先收集 C2 情报） | 确认最慢 857 ms，误封代价高 |
| U2R | 提权 | **告警 + 拉取上下文** | 稀有类，需人工确认 |
| **未知形态** | 模型没见过 | **不直接阻断**：限速 + 观察池 + 拉起抓包（见 §2） | 未知攻击误封业务的风险高于收益 |

**动作可用 `dry_run` 全程演练**（只告警不下发），上线前先跑影子模式。

### 1.3 处置可靠性【已实现】

| 机制 | 实现 |
|---|---|
| 幂等 | 同一源 IP 在封禁窗口内**不重复下发**规则（回归测试：5 次连续告警只下发 1 条，其余 4 条标注为幂等抑制）；**封禁窗口过期后必须重新下发**（防止幂等退化成"永久失灵"，已单独测试） |
| 审计台账 | 每条告警与每次下发都留痕，可反查"这条告警对应真实攻击 / 是真误报" |
| 动作分级 | drop / 限速 / 只告警，可按策略热切换（`/api/policy`） |
| 处置的可验证性 | 攻击注入后流量回落并记录，形成"攻击→告警→阻断→回落"完整证据链 |
| **下发后回读校验 + 失败回滚**（可选，默认关） | `verify_readback` 打开后：规则下发 → 发 `OFPFlowStatsRequest` 把流表**读回来** → 确认该源上挂着**动作正确**的规则（只"找到同源规则"不算通过：本该丢弃却变成限速同样是账实不符）；不一致或超时（超时=未确认）→ **回滚**（`DELETE_STRICT` 删规则，限速时连 Meter 一起删）并**解开幂等窗口**以便重试；每次校验单独写一条 `event=verify` 台账（含 `ok`/`found`/`rule_kinds`/`rolled_back`/原因）。注意 `executed=true` 只代表"消息已发出"，**不代表交换机上真的生效**——这正是本项要补的那一层 |

**原缺口已补齐**：下发后**未校验交换机是否真的生效** → 现已实现 `OFPFlowStatsRequest` 回读确认 + 失败回滚（见 §1.3）。
**已实测**（`tools/ryu_live_check.py`，19/19 项通过）：真实 `ryu-manager` + 真实 OF1.3 线协议下，适配层确实发出了
**带源 IP 匹配**的回读请求、控制器按请求 xid 正确配对回复、判定 `ok=true`，且**没有误回滚**（`event=verify` 台账可查）。
⚠️ 诚实边界：**回滚路径本身**（动作不符/超时 → `DELETE_STRICT` + 删 Meter + 解开幂等窗口）目前只有桩件回归测试覆盖
（`tests/test_ryu_guard.py` 新增 22 项 check），**未在真机链路上演练**——需要一个"收下 FLOW_MOD 却静默不装表"的交换机场景才能验证。

## 2. 未知攻击的处理（本体系最关键的一环）

### 2.1 先说风险有多大【已实现】

开集实验（训练时**整类拿掉**一类攻击，看系统是否诚实说"未知"）：

| 情形 | 实测结果 |
|---|---|
| **不做拒识** | 115/115 个未知攻击窗口**全部被贴上已知类标签**；留出 Botnet 时 **96% 被判为 Normal**、其中 74% 置信度 ≥ 0.9 —— **连告警都不会触发**（最危险的失效） |
| 做拒识（1% 误报预算） | 未知攻击检出率 UDR：U2R **69.8%**、Botnet **44.3%**；同期已知攻击被误拒仅 0.4%/0.5% |
| 拒识分数 | 跨场景 AUROC ≈ **0.978**；改进版加入 Mahalanobis + KNN 分数 |

**结论**：未知攻击的第一道防线不是"识别它是什么"，而是"**承认自己不认识**"。

### 2.2 三类告警 + 保守处置【已实现】

| 告警类型 | 触发 | 处置 | 状态 |
|---|---|---|---|
| 已知攻击（带细类） | 概率 ≥ 阈值 且 新颖性正常 | 按 §1.2 动作矩阵 | 【已实现】 |
| **未知形态** | 新颖性分数越阈（`unknown_threshold`，已标定 0.3914） | **不直接阻断** → 动作强制降级为限速（`unknown_action="throttle"`，**配置成 block 也会被降级**）+ 自动进待研判队列 | 【已实现】（阈值默认仍为 0=关闭，需按标定结果显式开启） |
| 正常 | 低于告警阈值 | 不动作；落在 `[0.5×阈值, 阈值)` 的窗口进观察池留痕 | 【已实现】 |

**为什么未知攻击不直接阻断**：未知 ≠ 恶意。误封一条正常业务链路的代价，可能高于放行一次可疑流量；
而"限速"既限制了可能的滥用，又不切断业务，给研判留出时间窗。

### 2.3 未知 → 已知的闭环【已实现】

```
未知告警 → 自动进待研判队列（带 review_id、新颖性分数、源/目的 IP、窗口号）
        → 人工确认（POST /api/review：verdict = attack:<类别> 或 normal）
        → 结论以 JSONL 回流落盘 results/review_feedback.jsonl
        → 下次重训直接读该文件作为标注来源，而不是靠人回忆
```
**这是未知攻击从"能发现"变成"能处理"的唯一途径**，现已落地为可调用接口（`GET/POST /api/review`、`POST /api/review/promote`）。
仍有一步未自动化：**回流文件到重训之间还没有定时任务**，目前需人工触发重训（见 §8）。

## 3. 漏报（未被识别）的处理

| 场景 | 处理 | 状态 |
|---|---|---|
| 低置信正常窗口 | **观察池**：`observe_margin × 阈值 ≤ 分数 < 阈值` 且未确认的窗口自动入池留痕（含窗口号、分数、新颖性、源/目的 IP），有界容量防内存膨胀 | 【已实现】 |
| 判为正常的窗口 | **环形缓冲留痕**（最近 `recent_windows` 个窗口的分数与判定），支持事后回答"这段为什么没报" | 【已实现】 |
| 漏报度量 | 片段级召回（比窗口级更严格）+ 逐类召回 + 每千条流漏报数 | 【已实现】 |
| 漏报代价 | 漏掉的片段持续时长 × 流量放大倍数（换算成影响面） | 【设计中】 |
| 已知会漏的地方 | 跨环境直接迁移 TPR@FPR=1% 仅 0.034~0.038；低速隐蔽攻击确认时延 857 ms | 【已实现】（实测并如实报告） |

## 4. 对抗与逃逸的处理

| 威胁 | 实测 | 处理 | 状态 |
|---|---|---|---|
| 白盒特征空间扰动（PGD） | ε=0.5 时逃逸率 **84.3%**、在线片段召回跌到 33% | **对抗训练**（clean + FGSM 各半）：宏 F1 收益 **+0.1237**，干净精度代价仅 **-0.0069** → 划算 | 【已实现】（**默认关**，可选开启：`--set adv_train_eps=0.2`；函数为 `src/train.py::fgsm_perturb` / `adversarial_augment`） |
| 随机扰动对照 | 同范数随机扰动逃逸仅 0.1% | 说明退化来自定向优化，非噪声 | 【已实现】 |
| 分布漂移（换网络/换工具） | 深度时序模型退化 **≤0.16 个百分点**；树模型退化 **3.8~7.7 个百分点**（ExtraTrees 0.8343→0.7961、RandomForest 0.8767→0.7996） | 优先时序深度模型 + 漂移监控 | 【已实现】 |

## 5. 阈值与工作点：不许拍脑袋

| 机制 | 说明 | 状态 |
|---|---|---|
| 误报预算驱动 | 阈值取自**拟合段正常流量**的 1−预算 分位，**从不看评估段** | 【已实现】 |
| 工作点全枚举 | 阈值 × 确认窗口数 × 窗口长度 在同一框架内枚举，输出 Pareto 表 | 【已实现】 |
| **标定必须在安静时段** | 反例实测：用含攻击的时段标定 → 阈值被推到 1.0、召回只剩 **4%** | 【已实现】（含反例记录） |
| **影子运行门槛** | 上线前不阻断跑一段，实际误报率 > 预算 ×3 → 拒绝开启自动阻断 | 【已实现】（`docs/07`） |
| 时间跨度可信度 | 跨度 > 168 小时即判定时间戳不可信，**拒绝**换算误报率 | 【已实现】 |
| **自动放松（自动降级）** | 人工复核结论 ≥ `autotighten_min_labeled` 条、且其中 `normal` 占比 ≥ `autotighten_normal_ratio`（默认 10 条 / 80%）→ 判定阈值**上调一档**（默认 +0.05），**有上限**（默认 0.9）、写审计台账、记 Prometheus；**默认关**（`CIDA_AUTOTIGHTEN=0`） | 【已实现】（默认关） |

## 6. 运维接口（把模型指标翻译成值班室听得懂的话）

| 输出 | 实测示例 | 状态 |
|---|---|---|
| 告警量/天、人工工时/天 | 真实数据（CIC-IDS2018，跨度 33.22 h，时间戳可信）：各臂折合 N=1 **14.45~35.62 工时/天**（约 2~4.5 个全职人力，**不可上线**）→ N=2 降至 **0.36~2.67 工时/天** | 【已实现】 |
| 误报/小时、P95 时延、漏报/天 | 工作点 A（阈值 0.99 + 确认 2，预算 10 次/h 内时延最优）：平均时延 **18.4 ms**、P95 74.4 ms、误报 8.23 次/h、漏报 0；工作点 B（阈值 0.5 + 确认 3）：误报 **0.66 次/h**、逐类片段 **80/80** 全检出 | 【已实现】 |
| 长稳表现 | 9.1 小时等价流量：内存 +13.6 MB、时延比 1.01、告警漂移比 1.14，三项判据全过 | 【已实现】 |
| 告警升级/降级状态机 | 升级：`_escalate()` 同源反复告警上抬动作；降级：`_maybe_autotighten()` 按人工复核结论上调阈值（默认关，见 §5） | 【已实现】 |

## 7. 处置决策表（一页速查）

| 新颖性 \ 攻击概率 | < 0.5×阈值 | 0.5×阈值 ~ 阈值 | ≥ 阈值（连续 N 窗口确认） |
|---|---|---|---|
| **正常** | 放行 | **观察池**（留痕待研判） | 告警 + 按细类动作矩阵 |
| **越阈（未知形态）** | 放行 | 观察池 + 抽样抓包 | **限速 + 未知告警 + 待研判队列**（不直接阻断） |

## 8. 缺口清单（按优先级，全部如实列出）

**已补齐的缺口**（每一项都有代码与回归测试；先是最初三个最高优先级缺口，随后逐轮追加）：

| 原缺口 | 落地方式 |
|---|---|
| 未知→已知闭环：待研判队列 + 回流 | `src/service.py` 的 `_enqueue_review` / `list_review` / `label_review` + `GET/POST /api/review`；结论以 JSONL 写入 `results/review_feedback.jsonl` |
| 观察池与环形缓冲 | `Observation` 数据类 + `self.observations` / `self.recent`（均 `deque(maxlen=…)`，有界）；`promote_observation` 可把观察项提升进研判队列 |
| 未知形态处置动作未定义 | 新增 `unknown_action`（默认 `throttle`）与 `_decide_action(..., unknown=True)`，**硬护栏：未知分支不允许升级为 `block`** |
| 告警升级/降级状态机 | `_escalate()`：同源在 `escalate_window_sec` 内告警达 `escalate_after` 次即自动上抬一级（`throttle`→`block`）。**安全设置优先**：`observe`（全局只观察）与白名单**永不升级**——`_decide_action` 与 `_escalate` 共用 `_protection_reason()` 单一判定，避免"两处各判一次、后来只改了一处"；未知分支最高只到 `throttle`；流重置时归零 |
| 观察池未附原始流记录 | `Observation.evidence`：随附窗口内流记录的**定位字段**（五元组/协议/标签），存字段子集而非全部 71 维特征，500 条观察项仍在 MB 级 |
| 长期运行的资源边界 | `self.alerts` 由**无上界 list** 改为有界 `deque`；累计量另用 `alerts_total` 计数（口径不受保留条数影响）。⚠️ 这是本轮排查中发现的真实隐患：长跑时内存只增不减 |
| 审计/回流文件无轮转 | `src/utils.py::append_jsonl` 支持按大小轮转 + 保留备份；`audit_alerts.jsonl` 与 `review_feedback.jsonl` 超限即滚动 |
| **写接口无鉴权** | `CIDA_API_TOKEN` 设置后，改策略 / 写研判结论必须带令牌（读接口保持开放，大屏不受影响）；未设置时完全放行 |
| **安全设置被自动升级推翻**（安全漏洞） | ⚠️ `_escalate()` 原先不知道 `_decide_action()` 里的两条兜底，导致**白名单里的控制器管理口/网关被反复告警升级成限速甚至阻断**、`observe`（只观察）也被升级。已抽出 `_protection_reason()` 作为**单一事实来源**，两处共用 |
| **`executed` 字段在说谎** | 原先 `executed = not dry_run`，于是 `observe` 动作也被记成「已执行」——而 observe 根本没有规则可下发。已改为 `(not dry_run) and action != "observe"`。这与 `ryu_guard.py` 早期"只记 True 却从未下发"是同一类错误 |
| **`review_id` 跨重启复用**（数据完整性） | ⚠️ `review_seq` 每次启动从 0 开始，而 `review_id` 是结论与证据之间**唯一的关联键**——重启后新旧记录共用 id，回流会拼出"同一窗口既有 attack 又有 normal"的矛盾样本，且**全程无报错**。已按历史文件（含轮转备份）恢复计数 |
| **回流数据不足以重训** | ⚠️ 这是排查中发现的更深的断点：`review_feedback.jsonl` 只有结论与分数、**没有特征**，人工标完也训不了模型。现新增 `results/review_evidence.jsonl`，把进入研判队列的窗口特征向量落盘，并**自带 `feature_names` 保证列序可追溯**；证据与结论按 `review_id` 关联，结论可改判而不必重复存特征 |
| **对抗训练不是可选项**（原清单第 3 项） | 抗逃逸能力此前只在实验脚本 `tools/adversarial_eval.py` 里，主训练流程没有入口。现已内建到 `src/train.py`：`Config.adv_train_eps`（**默认 0 = 关**，主流程与既有产物 sha256 不变）+ `fgsm_perturb` / `adversarial_augment`（L∞ 有界 + 投影回训练集物理可行域 + 标签逐行配对）。开启时先暖机若干轮再生成对抗样本——对随机初始化模型做 FGSM 等于加噪声，这一点写进代码注释与回归测试 |
| **只会自动升级、不会自动放松**（原清单第 6 项） | 长期高误报没有自愈路径。现新增 `_maybe_autotighten()`：由**人工复核结论**驱动（`review_feedback.jsonl`，含轮转备份，按 `review_id` 去重）自动上调阈值一档，**默认关**、有占比门槛、有上限、写审计台账 + Prometheus；开关与门槛既可由 `CIDA_AUTOTIGHTEN*` 设定，也可用 `POST /api/policy` 热更新 |
| **下发后未回读校验、失败无回滚**（原清单第 2 项） | `integrations/ryu_guard.py`：`verify_readback` 打开后下发即回读（`OFPFlowStatsRequest`，用 xid 把"校验回复"与"周期采集回复"分流），按**动作**判定是否真的生效；不一致/超时 → `DELETE_STRICT` 回滚（限速连 Meter 一起删）+ 解开幂等窗口 + 写 `event=verify` 台账。**默认关**：有些交换机对带 match 的 stats 请求响应很慢甚至不回，默认开会把"不确定"变成"回滚"，反而让处置形同虚设 |
| **多源证据融合（控制面 + 数据面）**（原清单第 5 项，**机制已落地、双源实测待产**） | `src/fusion.py`：两路证据按五元组归一与对齐（缺 IP 宁可不融合也不硬配错）、**冲突显式暴露**（一路报警、另一路判正常 → 取保守侧 + `conflict`/`review_required`，**不允许**用平均把对立抹平）、只有一路可用时标 `degraded`（不假装两路都在）、两路都不可用**不给分数**（不编造）；另有一条"弱证据一致"规则（两路都没到阈值但都达到 `阈值×0.5`）——这是融合唯一能超过单路的场景。⚠️ 诚实边界：**双视角实测数据尚未产出**（见 §8 剩余项），当前只有机制 + 回归测试，**材料里不得引用未产出的融合指标** |

仍在的缺口（编号沿用原清单，便于与历史材料对照）：

| # | 缺口 | 影响 | 优先级 |
|---|---|---|---|
| 1 | 回流**触发**仍是人工发起（`tools/retrain_from_feedback.py` 已能一键完成"拼数据集 → 混入训练 → 产出隔离的候选模型"，但没有定时/事件触发） | 闭环可走通，但不会自己跑 | 高 |
| 4 | 漏报代价换算（影响面）未做 | 漏报能查证但没折算成业务损失 | 中 |
| 5b | 多源融合的**实测数据**未产出（机制已在 `src/fusion.py` 落地并有回归测试） | 只能讲机制与护栏，不能给"融合提升多少"的数字 | 中 |

## 10. 运行期工程面（长期运行与安全）

前面九节回答"判得对不对、处置得对不对"，这一节回答"**它能不能连续跑几个月而不用人管**"。

| 关注点 | 做法 | 为什么 |
|---|---|---|
| 内存边界 | `self.alerts`、`self.observations`、`self.recent`、`self.review_queue`、`self.buffer_rows`、升级表全部 `deque(maxlen=…)` 或有界字典 | 服务是**长期常驻**的；无上界的容器会让内存只增不减。累计统计另用计数器，与保留条数解耦 |
| 磁盘边界 | `audit_alerts.jsonl`、`review_feedback.jsonl`、`review_evidence.jsonl` 按 `audit_max_bytes` 轮转，只保留 `audit_backups` 个历史文件 | 这些文件只追加不删除，不轮转会写满磁盘，也会让"出事回查"变成打不开的巨型文件 |
| 写入原子性 | 轮转用 `Path.replace`（同分区原子改名），当前文件始终可解析，不会写出半行 | 事故发生时正好在轮转，是最不能丢数据的一刻 |
| 写接口鉴权 | 设置 `CIDA_API_TOKEN` 后，`POST /api/policy`、`POST /api/review`、`POST /api/review/promote` 必须带 `X-API-Token` 或 `Authorization: Bearer …`；**读接口保持开放** | 能造成实际损害的是改策略（关掉演练模式、把动作改成 block）与写研判结论；大屏只读，不必持令牌。这是**纵深防御**——`DEPLOYMENT.md` 的 nginx Basic 认证仍是第一层 |
| 自动升级 | `_escalate()`：同源反复告警自动上抬动作级别（`throttle`→`block`），但 **`observe` 与白名单永不升级** | 持续攻击的特征是"反复触发"，单窗口判定看不出这一点；而安全设置必须压过任何自动行为 |
| 自动放松（自动降级） | `_maybe_autotighten()`：只认**人工复核结论**（≥N 条且 normal 占比 ≥X）→ 阈值上调一档，有上限、写审计、记 Prometheus；**默认关** | 长期高误报需要自愈路径，但"让系统自己变钝"是危险动作：所以默认关、只认人工结论、有上限（不会推到 1.0 把检测关掉），且每一次调整都可追溯 |
| 可观测 | Prometheus 暴露 `alerts_total`（计数器）、`escalations_total`、`review_pending`、`observations`、`unknown_windows` 等 | 值班室需要的是趋势与积压，而不是单次判定 |

相关环境变量（见 `deploy/cida-detect.env`）：
`CIDA_UNKNOWN_THRESHOLD`（未知标记阈值，0=关闭）、`CIDA_UNKNOWN_ACTION`（未知保守动作，默认 `throttle`）、
`CIDA_OBSERVE_MARGIN`（观察池下界比例）、`CIDA_API_TOKEN`（写接口令牌）、
`CIDA_AUDIT_MAX_BYTES` / `CIDA_AUDIT_BACKUPS`（台账与证据轮转）、`CIDA_REVIEW_EVIDENCE`（是否落盘研判证据）、
`CIDA_AUTOTIGHTEN` + `CIDA_AUTOTIGHTEN_MIN_LABELED` / `_NORMAL_RATIO` / `_STEP` / `_MAX`（自动放松的开关与门槛，默认关）。

**回归保护**：`tests/test_core.py` 中「自动放松需开关与人工结论」「有界告警与 JSONL 轮转」「告警升级状态机」
「观察池证据留存」4 项，加上前两轮的「未知动作护栏」「观察池与回看缓冲」「未知告警入队与回流」，
共 **7 项**覆盖本体系（另有 2 项对抗增广/确认语义一致性测试分别守 §4 与判定口径）。
