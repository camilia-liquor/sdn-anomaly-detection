## 一、这套系统由什么组成（三分钟版）

| 组件 | 位置 | 作用 | 不启动会怎样 |
|---|---|---|---|
| 检测服务 | `app/app.py`（+ `src/service.py`） | 滑窗判定、连续确认、告警、处置建议、审计台账、Prometheus 指标 | 整条链路停摆 |
| 演示大屏 | 同上，浏览器打开 `/` | 态势与审计可视化（迷你 SOC 控制台） | 不影响检测 |
| 控制器适配层 | `integrations/ryu_guard.py` | Ryu 侧采集流表统计 → 调服务 → 下发限速/阻断 | 只告警不处置 |
| 检测模型 | `artifacts/<tag>/model.keras` + `data/processed/` | 8 类分类 + 二分类异常判定 | 服务起不来（会明确报错） |
| 产物与报告 | `results/` | 指标、图表、事件报告、审计台账 | 不影响运行 |

**一条命令验证它活着**：`python tools/live_demo.py`（约 10 秒演完一场攻防）。

| 维度 | 承诺值 | 依据 |

> ② **首批**会慢约 0.5 秒（计算图构建），真实部署里只发生一次，容器重启后会再发生一次。

## 三、上线顺序（照这个顺序做，不要跳步）

- [ ] **1. 环境自检**：`python tools/check_env.py` → 全 ✓
- [ ] **2. 交付自检**：`python tools/acceptance_check.py` → **127 项通过、0 失败**（1 个警告是本机没装 Ryu，属预期）
- [ ] **3. 冒烟**：`python run_all.py --smoke`（约 20 秒，用独立目录，不会污染正式结果）
- [ ] **4. 观测一周（关键）**：用 `observe` + `dry_run=1` 起服务，**只看不动**，接入 `/metrics`
- [ ] **5. 标定工作点**：在一段**独立验证流**上按误报预算选阈值与确认次数（见第四节）
- [ ] **6. 接控制器但不下发**：Ryu 侧不加 `--execute`，观察一个完整业务周期
- [ ] **7. 打开处置**：`action=block`、`dry_run=0`，并逐条核对 `DEPLOYMENT.md` 第五节的安全清单

> 顺序背后的理由只有一句：**先证明"它不乱报"，再允许它"动手"。**

## 四、工作点怎么选（这是本系统最核心的运维旋钮）

三个旋钮：**判定阈值 × 连续确认窗口数 × 窗口长度**。三者共同决定"召回—时延—误报"的权衡，
且**不需要重训**即可切换。

```bash
# 在**验证流**（而不是测试流）上枚举，得到 Pareto 表
python tools/operating_point.py --tag <你的模型 tag> --budget 1.0
# 换算成运维语言（告警/天、人工工时/天、容量预警线）
python tools/ops_impact.py --attacks-per-day 20 --triage-minutes 6
```

实测工作点对照（出处 `results/ops_impact.md`）：

| 工作点 | 误报/小时 | 误报/天 | 告警/天 | 人工工时/天 | 平均时延 |
|---|---|---|---|---|---|
| 阈值 0.90 + 确认 1（**不做确认**） | 2.96 | 71.1 | 91.1 | 9.11 h | 11.8 ms |
| 阈值 0.50 + 确认 1（**不做确认**） | 8.56 | 205.4 | 225.4 | **22.5 h（≈2.8 个班次）** | 9.9 ms |
| 阈值 0.50 + 确认 3（**工程默认**） | 0.66 | 15.8 | 35.8 | 3.58 h | 18.1 ms |
| 阈值 0.90 + 确认 2（**误报预算内最优**） | 0.33 | 7.9 | 27.9 | **2.79 h** | 16.1 ms |
| 阈值 0.90 + 确认 3（**零误报点**） | 0.00 | 0.0 | 20.0 | 2.00 h | 19.5 ms |

**怎么用这张表**：先定"每天能投多少人工"（比如 3 小时），再挑满足这个预算里**召回最高、时延最小**的一档。

> **方法论提醒**：上表数字来自测试流，用于展示"旋钮怎么影响指标"；**真实上线必须在一段独立的验证流上定工作点**，
> 否则会有乐观偏差。本工程的默认配置（0.50 + 确认 3）是**不依赖任何测试集调参**的保守基线。

**另一个不必改阈值就能压误报的旋钮：加长窗口。** 窗口长度消融（T=16/24/32 均为 3 种子；出处 `results/window_ablation.md`）：

| 窗口 T | 种子 | 宏 F1 | 误报/小时 | 逐种子误报 | 平均检测时延 | 说明 |
|---|---|---|---|---|---|---|
| 16（默认） | 3 | 0.9938 ± 0.0012 | 3.29 ± 5.14 | 9.22 / 0.66 / 0.00 | 17.1 ms | 时延优先 |
| 24 | 3 | 0.9974 ± 0.0011 | 1.10 ± 1.90 | 3.29 / 0.00 / 0.00 | 24.3 ms | 折中 |
| **32** | 3 | **0.9979 ± 0.0024** | **0.11 ± 0.19** | **0.00 / 0.33 / 0.00** | **35.4 ms** | **误报优先的推荐工作点** |
| 48 | 1 | 1.0000（饱和） | 0.00 | 0.00 | 42.1 ms | 单种子且精度已饱和，不建议仅凭它选型 |

> **一句话**：若业务能接受约 35 ms 的检测时延，**T=32 用约 26 ms 的额外时延换掉约 84 倍的误报**
> （9.22 → 0.11 次/小时），而且**不动阈值、不动模型**，只改输入形状。
> 若时延预算只有十几毫秒，就留在 T=16，改用阈值标定与连续确认来压误报。
> **更值得注意的一点**：T=16 的误报在 3 个随机种子间**波动 14 倍**（9.22 / 0.66 / 0.00），
> 而 T=32 收敛到几乎为零（0.00 / 0.33 / 0.00）——**误报率本身飘 14 倍的系统是没法标定工作点的**，
> 所以"更稳"这一点的运维价值不亚于"更低"。
> ⚠️ T≥32 起测试集分类精度已经打满（宏 F1 1.0000），那里的"精度对比"衡量的是**指标天花板**而不是模型能力。

**"换个更难的网络环境，这个选型还成立吗？"——我们替你把这件事先测了。**
我们把数据难度拉满（类别重叠 0.70、隐蔽攻击片段占 80%、特征噪声 3 倍）重训了一整套（出处 `results/hard_ablation.md`），
给运维的结论只有三条：

1. **"有没有攻击"这件事没有退化**：难度翻倍后分类精度掉 5.4 个百分点、误报涨 4.5 倍，
   但**攻击片段召回仍然是 100%（30/30 个攻击片段全检出，与简单基准的 24/24 同为 100%）**。值班流程（有没有攻击 → 是什么类型 → 处置）里最关键的**第一问不受影响**。
2. **误报会涨，而且主要来自"像正常流量的攻击"**：困难基准上固定阈值 0.50 的误报从 3.29 涨到 14.88 次/小时。
   这**不代表模型变差**，而是流量本身变模糊了——**换环境后必须重新标定阈值**（见第四节），
   这也是本工程把"阈值 × 确认次数 × 窗口长度"做成**不用重训就能改的策略接口**的原因。
3. **别指望加长窗口能救极端环境**：困难基准上 T=32 的误报仍有 4.43 ± 1.68 次/小时（简单基准 0.11），
   窗口加长的收益在难度上来之后被大幅压缩。**先标阈值、再谈换窗口。**

> 复现：`python tools/hard_ablation.py`（幂等，只读产物、不重训；不出图也可只看 `results/hard_ablation.md`）。

**为什么"连续确认"这么关键**：它把误报从 8.56 压到 0.66 次/小时（−92%），
而**攻击片段召回没有任何下降**（都是 100%）——等于每天白省十几个人工小时。

## 五、值班预期：不同攻击要等多久

总体"平均 18 ms"会骗人。按类别拆开（出处 `results/per_class_online.md`，80 个逐类片段全检出）：

| 攻击类型 | 逐类片段 | 片段召回 | 平均检测时延 | 值班含义 |
|---|---|---|---|---|
| Probe | 8 | 100% | **5.5 ms** | 扫描特征极明显，几乎是即时 |
| DDoS | 18 | 100% | 13.5 ms | 洪泛一眼可见 |
| DoS | 16 | 100% | 27.4 ms | 单源持续，稍慢 |
| BruteForce | 9 | 100% | 43.6 ms | 需要几个往返才能确认 |
| WebAttack | 20 | 100% | 99.1 ms | 载荷特征在流统计量上较弱 |
| U2R | 5 | 100% | 164.2 ms | 样本极少的隐蔽攻击 |
| **Botnet** | 4 | 100% | **857.0 ms** | C2 心跳低速率长连接，**必须多看几条流** |

**结论**：**不要用一个统一的响应时限考核所有告警**。对 Botnet / U2R 这类隐蔽攻击，
系统"慢一点但报得准"是特性不是缺陷；若业务要求更快，应放宽阈值并接受更多误报，
而不是抱怨模型慢。

## 六、日常巡检（建议每天 5 分钟）

| 看什么 | 在哪 | 正常范围 | 异常怎么办 |
|---|---|---|---|
| 已处理流记录 / 窗口数 | `/api/stats` 或大屏顶部状态条 | 持续增长 | 不增长说明上游断了（见第八节 F4） |
| 确认告警数（按类） | `/metrics`：`sdn_ids_alarms_by_class_total` | 与业务基线同量级 | 某类突增 → 看第七节（未知标记） |
| p50/p95 判定时延 | `/metrics`：`sdn_ids_batch_latency_ms` | p50 ≈ 30 ms | 持续升高 → 查 CPU 与批次大小 |
| **未知窗口数** | `/metrics`：`sdn_ids_unknown_windows_total` | 占比平稳 | **占比突升 = 可能有新攻击或流量分布变化** |
| 滑窗重置次数 | `/metrics`：`sdn_ids_stream_resets_total` | 基本不增长 | 频繁增长 = 上游数据断续（见 F4） |
| 告警台账可写 | `results/audit_alerts.jsonl` 是否在增长 | 有新增行 | 检查磁盘与权限 |
| 服务健康 | `/api/health` → `{"ok": true}` | true | 见第八节 F1/F2 |
| 漂移面板（大屏） | 大屏「漂移与未知态势」面板，或 `GET /api/novelty?bins=60` | 未知占比平稳；游标随回放移动 | 占比或峰值格明显抬升 → 视为「流量形态变化」信号，结合告警一起看（**不要把熵高直接当成检测到攻击**，见第七节） |

## 七、可选能力：让系统说出"未知形态"

模型只在 8 类上训练过。遇到"没见过这种形态"的流量时，如果什么都不做，它会**自信地归到某个已知类**
（实测：留出整类攻击时 **100% 被安上已知标签**，其中 42%~74% 的置信度 ≥0.9；留出 Botnet 时 **96% 被判成"正常"**，
连告警都不触发——见 `results/openset_report.md`）。

```bash
# ① 在**正常窗口**上按误报预算标定阈值（不需要重训，约 5 秒）
python tools/openset_calibrate.py
#    → 实测推荐：entropy 阈值 0.3914（1% 预算）→ 正常被判未知 1.00%、已知攻击被判未知 0.30%

# ② 打开（运行时热更新，不用重启）
curl -X POST http://127.0.0.1:5000/api/policy -H "Content-Type: application/json" \
     -d "{\"unknown_threshold\": 0.3914}"
```

开启后熵超阈值的窗口判定类别显示为 `Unknown（未知形态）`，**照常告警与处置**，
只是不再声称具体类别 → 送进"待研判"队列，人工确认后回流训练集，形成 **未知 → 已知** 的闭环。

> ⚠️ **它不能替代告警，也不能解决所有未知攻击**：实测留出 U2R 时 1% 误报预算下能检出 69.8%，
> 但留出"像正常流量"的 Botnet 时只有 44.3%、0.1% 预算下 0.9%（`results/openset_report.md`）。
> 它的正确定位是**叠加在告警之上的"要不要人工研判"提示**，以及一条**免费的漂移指标**。

## 八、故障处置手册（症状 → 判断 → 动作）

| # | 症状 | 最可能的原因 | 动作 |
|---|---|---|---|
| F1 | 服务起不来，日志说"没有与预处理产物匹配的模型" | 模型与 `--processed-dir` 口径不一致 | 用 `--processed-dir` + `--model-tag` **成对**指定（服务有形状校验，会打印已尝试的候选清单） |
| F2 | `/api/detect` 返回 503 | 没跑过 `run_all.py`，或没装 TensorFlow | 看返回里的 `error` 字段；确认 `artifacts/` 与 `data/processed/` 都在 |
| F3 | 页面能开但显示"检测服务未启动" | 只有在线接口需要 TF；回放路径不需要 | 这是**优雅降级**，回放/注入/图表仍可用；要在线检测就装 TF |
| F4 | `sdn_ids_stream_resets_total` 一直涨 | 上游数据断续（控制器重连、采集重启、回放跳转） | **这是正常保护**（重置滑窗避免拼出伪窗口）；频繁则查控制器与采集链路 |
| F5 | 误报突然变多 | ① 流量构成变化 ② 阈值/确认被改小 ③ 上游字段口径变了 | 先看未知窗口占比是否同时升高；再核 `/api/policy`；必要时按第四节回退一档 |
| F6 | 某类攻击整段没报 | ① 该片段长度低于片段下限（口径内不计）② 阈值过高 ③ 确实漏报 | 用 `python tools/per_class_online.py` 看逐类召回；再对照 `results/operating_point.md` 回退阈值 |
| F7 | 大屏拓扑/曲线不动 | 回放已暂停或已到末尾 | 点"回到起点"；确认浏览器没用省电模式限制 `requestAnimationFrame` |
| F8 | 审计台账里有告警但交换机没变 | 策略是 `observe` 或 `dry_run=1`（**默认如此**） | 这是设计：先演练后执行。要真下发需 `action=block` + `dry_run=0` + 控制器加 `--execute` |
| F9 | 控制器日志报"检测服务不可达" | 网络/端口/服务未起 | **控制器侧 fail-open**：只记日志、不改流表，不会因为算法挂了把网络搞断 |

## 九、能力边界：**不要对外承诺这些**

| 做不到 / 未验证 | 现状 | 说明 |
|---|---|---|
| 物理交换机上的处置 | **未实跑** | 已完成的：真实 `ryu-manager` 进程 + 真实 OF1.3 线协议下全链路实测 16/16（`results/ryu_live_check.md`）、接口契约与下发路径 28 项桩件测试（`tests/test_ryu_guard.py`）。**未完成的：物理交换机、真实攻击流量、厂商私有扩展** |
| 长期稳定性 / SLA | **未测** | 只在数小时回放上验证，没有跑过 7×24 |
| 只有控制器、没有探针时的精度 | **宏 F1 0.8441** | 只用 OpenFlow 流表 17 列字段的实测值；片段召回仍 100%，但工作点要收到 0.99 + 确认 5，时延 18 → 41 ms。**字段缺口是工作点代价，不是功能失效** |
| 跨网络零样本迁移 | **不可用** | 自研数据训练的模型直接推理真实 inSDN：二分类 F1 0.5579、误报 20%；**且只重定标会让 AUC 从 0.67 掉到 0.47**（`results/cross_dataset_report.md`）。要上线必须在目标域标定/微调 |
| 加密流量的载荷分析、主机级取证 | **不做** | 本系统只做流统计量层面的检测 |
| 与"未知攻击检测器"等价的保证 | **没有** | 见第七节的实测边界（像正常流量的未知攻击检不出） |

## 十、变更管理：动这些东西之前必须做的事

| 要改什么 | 必须同时做 | 否则会怎样 |
|---|---|---|
| 换模型 | 模型 + `scaler.joblib` + `meta.json` **三者一起换** | 特征顺序不一致 → 判定全错（服务会做形状校验，能挡住维度不符，但挡不住同维度不同顺序） |
| 换数据口径 | `--processed-dir` 与 `--model-tag` **成对**指定 | 页面显示的模型与实际判定不是同一个 |
| 改阈值 / 确认次数 | 在独立验证流上重新标定，并更新巡检基线 | 误报/漏报比例整体漂移，历史对比失效 |
| 启用未知标记 | 在新环境正常流量上重跑 `tools/openset_calibrate.py` | 阈值不匹配 → 未知告警泛滥或形同虚设 |
