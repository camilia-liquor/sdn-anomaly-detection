# 答辩要点、现场操作卡与参数速查

## 一、30 秒电梯陈述

> 我们做的是 SDN 环境下的网络流量异常检测，而且做的是**一个能接进控制平面的系统，不是一份实验报告**。
> 核心模型是 **CNN + BiLSTM 混合网络**：CNN 从"连续若干条流记录"里提取局部行为模式（突发 SYN、等间隔心跳），
> BiLSTM 对窗口内的时间依赖双向建模，输出端是多分类头加二分类头的**多任务结构**。
> 针对比赛我们做了四件事：**自带可复现的仿真数据生成器**（与 Ryu 采集脚本、公开 inSDN 数据集格式一致）、
> **修正了原始 demo 的数据泄漏与评估口径错误**、**在线告警级评估**（检测时延、次/小时误报率），
> 以及**把它包成了一个可被控制器调用的服务**——有 `/api/detect` 接口、有处置策略与白名单、
> 有演练模式、有可追溯的审计台账、有 Prometheus 指标，还有一份部署文档。
> 现场可以直接演示：点一下"注入攻击"看告警，再切到终端看控制器闭环把告警真的变成限速/阻断规则。

## 四、评委常见问题与参考回答

**Q1：数据是自己仿真的？那结果可信吗？**
A：三点。① 生成器不是随机撒点，而是按攻击机理建模（速率、时长、标志位、到达间隔），
特征之间物理自洽，例如 `Flow Packets/s = 总包数/时长`；
② 输出格式与公开数据集 inSDN/CICFlowMeter 列名逐字一致，也与本仓库 Ryu 采集脚本完全一致，
所以**换成真实采集数据只要改一个参数**（`--source real --real-data-dir ...`）；
③ 我们主动加了类别重叠（15%）、标注噪声（1%）、量测噪声，避免指标虚高。

**Q2：怎么保证没有数据泄漏？**
A：四道防线：时序切分（不随机打乱）、切分边界留 purge 间隙、滑窗不跨集、
`StandardScaler` 只在训练集 fit。这四点原 demo 全部踩了（见 `docs/01`）。
另外我们不用测试集做早停/调参，只用一个独立的验证集。

**Q3：为什么 CNN 和 BiLSTM 都要？单独一个不行吗？**
A：见消融实验表。CNN 单独用丢掉了时序演化信息，BiLSTM 单独用容易被局部噪声带偏；
两者串联后宏 F1 和在线片段召回都更好。这个结论是我们自己跑出来的，不是拍脑袋。

**Q4：你的 AUC 很高，是不是任务太简单？**
A：（如果数字确实高）我们做了两组压力测试：把类别重叠比例从 0.15 提到 0.30、
标注噪声提到 5%，指标会明显下降，说明模型确实在学边界而不是背数据；
另外分布漂移测试集（`drift_strength>0`）用来验证鲁棒性。

**Q5：上线怎么部署？**
A：Ryu 控制器侧每 N 秒拉一次流表统计（就是 `collect_*_traffic.py` 的做法），
按同样的特征顺序拼成一条流记录，进滑窗缓冲；窗口满即推理一次。
单窗口推理在 CPU 上是毫秒级，控制器完全带得动；阈值可按误报预算现场调
（`06_binary_detection_*.png` 给了阈值-F1 曲线）。

**Q6：攻击样本很少，模型会不会全判正常？**
A：用逆频类别加权（`sample_weight`），并同时报告**宏平均 F1**（而不是被正常流量主导的加权 F1）。
逐类召回率在 `results/per_class_*.csv` 里可以逐条看。

**Q7：为什么不用 Transformer / 图神经网络？**
A：我们的窗口只有 10 个时间步、特征几十维，Transformer 的表达能力用不满，
反而更容易过拟合；GNN 适合拓扑建模，但当前数据里拓扑信息（交换机间关系）没有进入特征，
属于我们下一步要补的方向。选型是**按数据规模**来的，不是按热度。

**Q8：误报率大概什么水平？**
A：默认配置（连续 3 窗口确认）下**平均 0.55 次/小时**，攻击片段召回保持 **100%**。
更重要的是我们给了**完整的误报–时延权衡表**：同一模型可以在 0 ~ 11 次/小时之间自由换点 ——
不确认时 8.56 次/小时（9.9 ms），确认 3 个窗口降到 0.66 次/小时（18.1 ms），
"阈值 0.90 + 确认 3"可做到 **0 误报**（19.5 ms）。这份表由 `tools/operating_point.py` 一键生成、可复现，
运维按误报预算挑点即可。**这正对行业第一痛点：2025 SANS 调查显示 73% 的组织把"误报"列为威胁检测最大挑战。**

**Q9：为什么要报"次/小时"而不是误报率比例？**
A：比例会被正常流量总量稀释，运营方关心的是"一天要处理多少条告警"。所以我们两个都给：
窗口级 FPR 比例用于和其他论文对比，次/小时用于回答"能不能用"。

**Q9b：模型错在哪里？**
A：我们对 3,513 个测试窗口做了完整错误分析：总错误 17 个（0.48%），**漏报为 0**，
全部是"正常流量被误判为攻击"；误报集中在 4 组混淆对（Normal→BruteForce 占一半），
且错例的共同特征是**包长偏小** —— 与暴力破解/扫描类攻击的机理（小包高频）天然重叠。
这就是下一步补样本与做特征工程的着力点。

**Q9c：这套东西能真接上 SDN 控制器吗？**
A：能，有实测性能基准：模型本身单窗口推理 **p50 0.92 ms**，批量 256 时 **0.022 ms/窗口**
（≈13.6 万条流记录/秒），普通 CPU 无需 GPU。
注意 Keras `predict()` 每次调用有约 36 ms 固定包装开销，所以工程上应**按控制器采集周期攒批推理**，
而不是来一条算一条——这条建议也写进了报告。

**Q9：注意力热力图能说明什么？**
A：它能说明模型把权重放在了窗口里哪几条流上。答辩时我们展示攻击窗口的注意力更集中在
"突发开始"的几个时间步，这与人看流量时的直觉一致 —— 这也是模型可解释性的一个落点。

**Q10：和原 demo 比，你们改了什么？**
A：一句话：**同样的算法思路，正确的实现与评估**。三处硬伤：随机切分导致的数据泄漏、
二分类损失训多分类、用硬标签算 AUC。逐条对照见 `docs/01_原始代码问题清单.md`。

**Q11：为什么 CNN 分支的增益不明显？**
A：（如实回答，**这题大概率会被问到，而且我们现在有一个很强的答案**）消融显示去掉 BiLSTM 分支后宏 F1 从 0.985 掉到 0.943，
而单独 BiLSTM 是 0.988 —— 也就是说在流统计量这种"已经聚合过"的特征上，**循环结构是主要贡献者**。

**不要只说"我们如实报告了"——要说我们主动把它测穿了**（这是本题的加分点）：

1. 我们一开始的解释是"窗口还不够长"，于是把窗口一路做到 **T=48**：Δ 从未转正，到 T=48 双方都打满 1.0000（天花板）。
2. 这个解释还有一个更容易被反驳的地方——**"那是你数据太简单"**。所以我们**另造一套困难基准**：
   类别重叠 0.35→**0.70**、隐蔽攻击占比 0.45→**0.80**、特征噪声 ×3，难度拉满后重训一整套。
   先证明难度真的上去了（与架构无关的线性探针宏 F1 **0.9807→0.8658**），且**没有任何结构再打满**。
3. 结果：**卷积依然没有增益**——四个窗长 Δ 全为负、最好单分支每个 T 都是"仅 BiLSTM"，
   更硬的一层证据是**逐种子配对 6/6 为负**（符号检验双侧 **p=0.031**）；而且**窗口越长 Δ 反而越负**，
   "需要更长上下文"这个解释**被我们自己的实验推翻**。
4. 我们还给出**可解释的原因**：卷积单支在困难基准上掉得最狠（T=32 宏 F1 0.8484，比简单同档低 0.1356）；
   混合模型是"过拟合式增益"（训练准确率更高、测试宏 F1 更低，参数 151k vs 96k）。
   机理是流统计量把"每条流的聚合量"当时间步，卷积要找的局部组合模式在特征工程阶段已被压平——
   **价值应当去原始包序列/字节级输入里找，而不是继续当作精度来源**。
5. **最后一定要补这一句**（把负面结论转成正面价值）：同一批实验显示，难度翻倍后分类精度掉 5.4 个百分点、
   误报涨 4.5 倍，**但攻击片段召回仍然是 100%**——**精度指标在退化，安全底线没有退化**，
   这正是我们把"攻击片段召回"而不是"宏 F1"写成第一指标的原因。

**答这道题的要点**：不要辩解，直接给出"我们自己造了最好的翻盘机会，它依然没有翻盘"这套完整链条
（`results/window_ablation.md` + `results/hard_ablation.md`）。
评委通常更认可这种"知道自己模型边界在哪、并且**主动去证伪自己**"的回答。

**Q12：你们这套东西，攻击者能不能绕过？（对抗鲁棒性）**
A：能，而且我们**量化了**（`results/adversarial_eval.md`）。白盒、特征空间、L∞ 有界的定向扰动下：
**ε=0.30 时逃逸率 73%**（宏 F1 0.9930→0.4802），ε=0.50 时 84%；而**同范数随机扰动几乎无效**（宏 F1 ≥0.9887）
——说明这是**优化出来的攻击**，不是"加噪声就崩"。在线口径更直观：无攻击 24/24 片段全检出，ε=0.2 时 14/24、ε=0.5 时 **8/24**。
**缓解**：对抗训练（clean+FGSM 各半）在 ε=0.2 处把宏 F1 从 0.6083 拉回 0.7312（收益 +0.1237），干净精度只掉 0.0069
→ 按事先写死的判据（收益 > 代价）是"**划算的缓解**"。**两点必须说清**：① 本实验是特征空间攻击，
给的是**脆弱性上界**，不代表攻击者一定能在报文层实现；② 我们试过用工程里已有的**熵阈值**拦对抗样本——**拦不住**
（熵 0.0177 → 0.013~0.032，阈值 0.3914），这条负面结论如实写在报告里。黑盒/查询式攻击留作后续工作。

**Q13：那"卷积没用"到底是没用还是没测对？（包序列复研）**
A：两条都测了，结论是**分层**的（`results/packet_seq.md`）：① 在**流级聚合量**上卷积确实没有价值——窗口做到 T=48、
难度拉满的困难基准、逐种子配对全部为负；② 但"局部模式被特征工程压平"这个解释可以被检验：把输入换成**流内有序包序列**
（同一批 24,000 条流、同数据对照）后，"卷积落后最好单分支"从 **0.1354 缩到 0.0071（19 倍）**，
且包级 **T=32/64 出现逐种子配对 3/3 为正的正增益**（+0.0155/+0.0282）——**全项目第一次出现混合结构的正增益**。
**但不夸大**：包级绝对宏 F1 只有 0.31~0.39（流级 0.968），所以这是**机理探测**，不等于"包级模型更好用"；
总判定写 `mixed`（换成全量参照时只有 T=32 通过），两个参照都报。

**Q14：没有探针、只有流表统计，你们还能用吗？（控制器字段扩展）**
A：这正是本轮补的最大一块（`results/ctrl_field_extension.md`）。只用 OpenFlow 流表统计的 17 列时宏 F1 0.8183、
须阈值 0.985 + 确认 5、时延 39.8 ms；但我们发现**那 17 列不是控制器能拿到的全部**——控制器还能在轮询窗口内做**流表聚合**：
一个源打过多少不同目的端口（扫描）、多少源打同一目的（洪泛）、短流占比、新建流速率、目的端口熵……
补上这些**只由流表字段推导**的量后（17 → 30 列），宏 F1 升到 **0.9956**，**追平 84 列 CICFlowMeter 口径（0.9940）**，
工作点还更宽松（阈值 0.985→0.3、确认 5→2、时延 39.8→14.0 ms）。
**两条诚实说明**：聚合窗口是**因果的（只看过去 60 秒）**——最初写成对称窗口（含未来行）属于前视泄漏，已修正重跑；
TCP 标志位、IAT/包长分布这些量 **OpenFlow 流表本来就不提供**，我们不去伪造，报告里列了"不可得清单"。

**Q15：新型攻击没见过怎么办？（开集 + 本轮改进）**
A：做了留出整类攻击的实验，并且本轮把它**大幅改善**了（`results/openset_ood_plus.md`）。不做拒识时
**100% 的未知攻击被自信错判**（Botnet→Normal 96%，连告警都不触发）；原三种分数在 1% 预算下 U2R 69.8%、**Botnet 仅 44.3%**。
本轮改用**特征空间马氏距离**（类条件均值 + 共享协方差）后，U2R 与 Botnet 的 **UDR@1% 双双 100%**，
最严预算 0.1% 下 Botnet 从 **0.9% → 90.9%**。**我们做了自我怀疑诊断**：只看"特征范数偏离"的检出率仅 0.4%~5%
→ 提升不是平凡信号；代价是已知攻击误拒从 0.5% 升到 3.0%~6.1%，所以判定是 `partial` 而非"完美"（KNN 分数无效，也如实列出）。

**Q16：域随机化不是标准解法吗？为什么你们说不行？**
A：因为我们**真的做了**（`results/domain_randomization.md`）——6 个域逐个留一域零样本，并加"同样本量、更多多样性"的等预算对照。
结果：**平均只 +0.0063、3 正 3 负（p=1.0）→ 不奏效**；结构上对"老式明显攻击" **+0.22**、"类别边界模糊" **+0.10**，
但对"隐蔽攻击为主" **−0.25**——**强烈依赖目标域类型**；等预算对照在 **5/6 折比单域更差**，
说明该难度下**"每域数据量"比"域数量"更重要**。这条负面结论的价值是：把上一版报告里"下一步建议：域随机化"
从**设想**变成**已被检验的答案**。（另记录一个方法论坑：用"复制同一域"对齐数据量会因管线去重而两次结果逐位相同。）

**Q17：跑了多久？会不会越跑越慢/内存泄漏？（长稳回放）**
A：`tools/soak_test.py` 让进程内服务连续回放 **9.1 小时等价流量**（3 轮 × 3.04 h、36 桶、不限速）：
内存 **+13.6 MB**（门槛 ±64）、末段/首段时延比 **1.01**（门槛 ≤1.5）、前后半段告警漂移比 **1.14**（门槛 ∈[0.5,2]）→ 三项判据全过。
**边界**：这是本机进程内回放，**不能**替代真实生产网络的长期运行验证，报告里如实标注。

**Q18：到了现场第一步做什么？（现场标定）**
A：`tools/calibrate_online.py`（`results/calibration.md`）：取一段**安静时段**的流量，按业务能接受的误报预算
（如 1 次/小时）**反解**阈值与确认次数，可 **`POST /api/policy` 热写回**正在运行的服务并回读校验，然后用带标注的一段回放核对召回/时延/误报。
**最有说服力的证据是一个反例**：如果拿**含攻击的时段**去标定，阈值会被推到 1.0，整条流召回从 100% 掉到 **4%**——
这就是"现场标定必须挑安静时段"的量化证据。工具还带**样本充足性判据**（预算 B 次/小时至少需要 3÷B 小时安静流量）。

**Q19：你们在真实 Ryu / 真实交换机上验证过吗？**
A：**物理交换机上没有——这一点不掩饰**（本机没有 SDN 硬件）。但**真实 Ryu 控制器 + 真实 OpenFlow 1.3
线协议这一层，我们已经实跑并留证**：本机装了 Ryu 4.34（独立 venv），用官方 `ryu-manager` 加载我们的
适配层（不是桩件），再起一个模拟 OF1.3 交换机，用真实 TCP + 真实报文完成握手、上报流表统计
（正常轮 + 攻击轮，流量取自真实数据集的测试流），然后逐字段解析控制器回发的 `OFPFlowMod`。
结果 **16/16 项检查通过、Ryu 侧零解析错误**：攻击轮触发告警后，交换机实收一条 `priority=100`、
按可疑源 IP 精确匹配、指令为「空 action 列表 = DROP」的流表项；审计台账 `executed=true` 与报文逐项对上；
正常轮**一条规则都没下发**。证据在 `results/ryu_live_check.md`（含握手时间线、逐条报文、台账）。
**更值得讲的是过程中抓到的 4 个真 bug**（全是「单元测试永远发现不了」的那类）：
① multipart 子类型写错（`OFPMP_FLOW` 写成 0 = `OFPMP_DESC`），Ryu 拿 1056 字节的 desc 结构去解流表，
   直接抛异常丢弃整包——**链路上一切正常，控制器却永远不告警**；
② OF1.3 握手比想象多一步：Ryu 收到 `FEATURES_REPLY` 后**不会**进 `MAIN_DISPATCHER`，
   还要交换机回一条 `OFPPortDescStatsReply` 才进；少了它，适配层的 datapath 列表永远是空的；
③ OXM TLV 之间**不该**逐条补齐（只有整个 match 补齐），自己发自己收完全自洽，只有真实 Ryu 会拒绝；
④ 适配层的处置幂等：同一次攻击会连报十几个滑动窗口，早期实现会往交换机塞十几条重复规则。
所以准确表述是：**真实 Ryu + 真实 OF1.3 线协议已实测通过，物理交换机与真实攻击流量仍未覆盖**。
评委若要复现：先 `python tools/ryu_live_check.py --self-test`（秒级、免装 ryu），
再 `--ryu-python <装了 ryu 的解释器>` 跑整套。

**Q20：你们和已发表的方法比过吗？凭什么说自己的方案更好？**
A：比过，而且是**同一份数据、同一套切分、同一套训练与评估代码**下比的——不是拿论文的数字比我们的数字。
对标对象是《通信技术》2026 年第 8 期的《基于 PLO-BiLSTM 的网络异常流量检测方法》（南京邮电大学），
它的框架是「bPLO 特征选择 + BiLSTM 分类 + 四模型对比 + 特征选择消融」，我们把这套框架**补齐并跑通**：

1. **特征选择环节**（我们原来缺的那一环）：按论文公式实现了二值化极光优化 bPLO
   （式 1~11：回旋运动 / 极光椭圆漫步 / 粒子碰撞 / Sigmoid 二值化 / 适应度 `γ·误差 + β·|R|/|D|`），
   并配 PCA、PSO、不选特征三个对照，两边各跑 3 个种子。见 `results/feature_selection.md`。
2. **外部对照模型**：论文的对比组是 RNN / LSTM / BiLSTM / Transformer，我们把这三个补进
   模型变体表，加上原有 CNN 与双分支主模型，共 6 个模型同口径跑完。见 `results/published_baselines.md`。
3. **参数敏感性**：论文表 4 研究了 bPLO 的「质量 m」，我们也做了 m ∈ {50,75,100,125} 的对照。

**三条必须说清楚的话**（评委最容易追问的地方）：
- **数字不可直接比较**：论文用 CICIDS2017 / UNSW_2018_IoT_Botnet、**7:3 随机划分**、Min-max 归一化、
  以 Accuracy 为主指标；我们用自研数据集 + 控制器原生字段口径、**时序切分 + purge gap**（防泄漏）、
  宏平均 F1 + 在线告警口径。数据集、划分、指标三处都不同，能比的只有「方法是否有效」这个结论。
- **我们比论文更严的地方**：① 特征**只在训练集上选**（论文在全量数据上选，属选择偏差）；
  ② 不做随机划分（随机划分会让同一段攻击的相邻窗口同时进训练与测试，指标虚高）；
  ③ 同时报在线口径（片段召回 / 告警时延 / 误报次数每小时），而不是只报 Accuracy。
- **我们如实保留的不利结果**：① bPLO 的适应度用**代理分类器**（逻辑回归）而不是完整深度模型
  （300 次适应度评估各训一次深度模型在算力上不可行），这是明确的工程近似，报告里已标注；
  ② 我们还量化到一条方法学观察：论文式(3) 的常数项 `LB + r1×(UB−LB)/2` 在二值化后会让
  **选择率系统性偏高**（实测约 65%~70% 的特征被保留），而抑制项 `β|R|/|D|` 在 β=0.01 时
  不足以抵消它——这是**按论文公式实现的必然结果，不是实现 bug**，我们的自检把这一点记成
  「观测」而不是断言，并在报告里把 |R| 单列一列。这条观察对任何做二值化群智能特征选择的人都有用。

**为什么这件事值得做**：作品里最容易被问倒的一句话是「你自己造数据、自己定指标，凭什么说好」。
把一篇同领域已发表论文的框架完整复现并做同口径对照，等于把「自证」变成「他证」。
